Crosswalker ships recognized-source imports for the framework files below today. This page is the canonical technical reference for obtaining each source, choosing the matching [recipe](/crosswalker/concepts/terminology/#recipe), selecting the exact worksheet and header row, checking the real record count, and avoiding imports that look successful but are wrong.

**Status last verified:** 2026-09-23 — nested stack recipe IDs and layouts verified against `recipes/import/nist-800-53-nested.json` and `recipes/import/cri-profile-v2-2-nested.json`; historic source row counts retain their earlier verification.

The bundled recipes live in the [Crosswalker plugin repository](https://github.com/cybersader/crosswalker/tree/main/recipes/import). Community recipes and contribution guidance live in [crosswalker-recipes](https://github.com/cybersader/crosswalker-recipes). Framework content is not bundled: obtain each source from its publisher and confirm that the publisher's terms fit your use.

## Silent-failure checklist

> [!danger] Check these before trusting an import
> These failures can produce plausible row counts, valid-looking notes, or no error at all.
>
> 1. **CIS float collapse:** safeguard identifiers are numeric cells. A raw-value reader turns `4.10` into the float `4.1`, colliding with safeguard `4.1`. One note disappears silently. Crosswalker reads formatted cell values to keep the identifiers distinct.
> 2. **CRI header index:** the CRI v2.2 header is at row **index 2**. Index 1 still returns the correct 472 rows, but names every column `__EMPTY`, so a row-count-only check falsely passes.
> 3. **NIST line counting:** the NIST SP 800-53 CSV has about 2,605 physical lines because control text contains embedded newlines, but it has **1,189 records**. `wc -l` does not measure CSV records.
> 4. **Row selection:** the CSF workbook has 46 banner rows; the two CIS recipes share one sheet containing two row kinds; and the two CPRT recipes encounter 227 non-concept elements. Pointing a recipe at a collection that mixes row kinds is what silently collapses rows onto empty or duplicate paths. Each of those five bundled recipes now declares its own row predicate, so you can point it at the full source collection and skip the manual prefilter that used to be required. A recipe you write yourself still needs one: a source that mixes row kinds and a recipe that does not say which kind it wants is the failure.
> 5. **SCF width and volume:** the SCF workbook is 369 columns wide. Naive automation can throw `RangeError` while enumerating a row. Its practical scale pressure is about 9 MB of generated body text, not its 1,468-row count.

## Stack detail variants

The [framework stack](/crosswalker/getting-started/quick-start/) selects `nist-800-53-r5-nested` and `cri-profile-v2-2-nested` for its NIST 800-53 and CRI slots. Ordinary file recognition continues to propose `nist-800-53-r5-flat` and `cri-profile-v2-2-flat`. The nested NIST variant makes family folders, control folder notes, and enhancement notes; family folders have no concept notes, so family-level mapping endpoints remain unresolved pending a separate identity-safe design. The nested CRI variant makes function, category, and subcategory folder notes and diagnostic-statement notes. Both keep their flat counterpart's source binding, frontmatter, and body projections (source: `recipes/import/nist-800-53-nested.json`, `recipes/import/cri-profile-v2-2-nested.json`).

Choose **Notes for top levels only** to omit NIST enhancements and CRI diagnostic statements for that run; ATT&CK and CSF are unchanged. This is a row filter, not a rewrite of the bundled recipes (source: `src/import/stack/stack-model.ts` and `src/import/run-recognized-import.ts`). Switching detail on an existing import set is not supported yet. Start a new set for a different detail level; refresh an existing set only with its recorded recipe.

## Licence posture

This is a practical pointer, not legal advice and not a replacement for the publisher's terms. Importing a file for your own use, redistributing the source, and sharing generated notes are different acts. Confirm the terms for the exact version, fields, audience, and use involved.

| Source | Practical posture |
|---|---|
| NIST publications | NIST describes its US Government works as generally not subject to US copyright; check the [NIST copyright policy](https://www.nist.gov/oism/copyrights) and any third-party notices in the specific publication. |
| MITRE ATT&CK | MITRE permits use subject to its [ATT&CK terms of use](https://attack.mitre.org/resources/legal-and-branding/terms-of-use/), including attribution requirements. The bundled recipe carries the MITRE notice into generated notes. |
| CIS Controls | The publisher applies restrictive terms, including CC BY-NC-ND language. Registration is required to obtain the workbook. Confirm whether sharing generated notes is permitted for your situation. |
| CRI Profile | CRI's [Profile FAQ](https://cyberriskinstitute.org/the-profile/profile-faq/) describes restrictive CC BY-NC-ND terms. Confirm whether sharing generated notes is permitted for your situation. |
| Secure Controls Framework | SCF publishes CC BY-ND language plus separate terms governing use and derivatives. Read the [SCF terms and conditions](https://securecontrolsframework.com/terms-and-conditions) and confirm your intended use. |

## NIST SP 800-53 Rev. 5

**Obtain it:** [NIST SP 800-53 Rev. 5, Update 1](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final). NIST publishes spreadsheet/CSV material alongside the publication. Machine-readable OSCAL is also available from [usnistgov/oscal-content](https://github.com/usnistgov/oscal-content/tree/v1.4.0/nist.gov/SP800-53/rev5/json), but it is a different lineage and can produce different counts and hashes.

**Bundled recipe:** `nist-800-53-flat`, from the [bundled import recipes](https://github.com/cybersader/crosswalker/tree/main/recipes/import). It reads the CSV lineage and produces one flat note per control or enhancement.

### Exact binding and result

| Item | Verified value |
|---|---|
| Source shape | CSV with header at index 0 |
| Records | **1,189** |
| Physical lines | About 2,605 because quoted control text contains embedded newlines |
| Key columns | Control Identifier; Control (or Enhancement) Name; Control Text; Discussion; Related Controls; Control Family |
| Result | 1,189 notes; related controls become a queryable property and body wikilinks |

### Identifier format

Pattern: `[A-Z]{2}-\d+(\(\d+\))?`

- Family: `AC`, `AU`, `CA`
- Control: `AC-1`, `AC-2`
- Enhancement: `AC-2(1)`, `AC-2(13)`

### Gotchas

- **Do not count records with `wc -l`.** Embedded newlines explain the gap between about 2,605 physical lines and 1,189 CSV records.
- **Preserve enhancement parentheses.** A custom filename transform that strips rather than sanitizes punctuation can make `AC-2(1)` and `AC-2(13)` collide.
- **Clean the related-controls field.** Empty rows can carry `[None]`, and identifiers can have trailing punctuation. Without cleanup, links such as `[[SC-37.]]` and `[[[None]]]` render but do not resolve.
- **No row prefilter is needed** for this lineage: every record represents a control or enhancement.

### Assessment procedures

**Source:** [SP 800-53A Rev. 5 assessment procedures](https://csrc.nist.gov/pubs/sp/800/53/a/r5/final)

Assessment identifiers need normalization before joining to controls:

```text
AC-01_ODP[01]  →  AC-1
Pattern: /^([A-Za-z]+)-0?(\d+)/
```

## NIST CSF 2.0

**Obtain it:** [NIST Cybersecurity Framework](https://www.nist.gov/cyberframework). The core workbook and a [Cybersecurity and Privacy Reference Tool (CPRT)](https://csrc.nist.gov/projects/cprt) export have different shapes and are not interchangeable.

**Bundled recipes:**

| Recipe | Reads | Output |
|---|---|---|
| `nist-csf-2-flat` | Core workbook, sheet `CSF 2.0` | One note per subcategory |
| `nist-csf-2-cprt` | CPRT JSON | Flat element notes |
| `nist-csf-2-cprt-hierarchical` | CPRT JSON | Function/category hierarchy |
| `nist-csf-2-withdrawal-lineage` | Derived edge list from the core workbook | One `superseded_by` crosswalk edge per replacement of a withdrawn subcategory |

### Exact workbook binding and result

| Item | Verified value |
|---|---|
| Sheet | `CSF 2.0` |
| Header row | **Index 1**; row 0 is a banner |
| Parsed rows | 231 total |
| Importable subcategory rows | **185** |
| Banner rows | **46** |
| Withdrawal markers | **79 of the 185 subcategory rows** |
| Key columns | Function; Category; Subcategory; Implementation Examples; Informative References |

Identifier pattern: `[A-Z]{2}\.[A-Z]{2}-\d{2}`, for example `GV.OC-01`.

### Gotchas

- **The workbook mixes banner rows with subcategory rows.** Only rows with a non-empty `Subcategory` are real; the other 46 resolve to empty filenames and collide. The bundled recipe declares that selection itself, so no manual prefilter is needed.
- **The CPRT collection includes 227 non-concept elements** (225 `sort` ordering keys and 2 `party` elements) that must not become concept notes. Both bundled CPRT recipes exclude them by element type, leaving **679** concept elements.
- **Withdrawal markers are real rows, and they carry lineage.** Of 185 subcategory rows, 79 are withdrawal markers naming the CSF 2.0 subcategories that replaced them. If you count only active outcomes, the total is 106. See [Withdrawal lineage](#withdrawal-lineage) below for what the markers look like and how to import them.
- **Merged-cell hierarchy columns are empty on subcategory rows.** The bundled flat recipe derives function and category from the subcategory identifier rather than trusting those cells.
- **Outcome text repeats the identifier.** The bundled flat recipe projects the cell verbatim, prefix included. That is now a deliberate choice rather than a grammar limit: `{Subcategory|regex(:\s*(.+)$)}` recovers everything after the first colon on all 185 rows, but changing the shipped recipe would move its hash and rewrite every already-generated note.
- **Informative References is intentionally omitted.** It contains newline-separated mappings whose labels and identifiers need per-item cleanup before they can become reliable links.

### Withdrawal lineage

CSF 2.0 does not just mark a v1.1 subcategory as gone: it says what replaced it. That statement is machine-readable, but it is written in prose inside the `Subcategory` cell.

```text
ID.AM-06: [Withdrawn: Incorporated into GV.RR-02, GV.SC-02]
ID.GV-03: [Withdrawn: Moved to GV.OC-03]
ID.RM-03: [Withdrawn: Moved into GV.RM-02]
```

| Item | Verified value |
|---|---|
| Withdrawal markers | **79** of the 185 subcategory rows |
| Successor references | **127** across those 79 markers |
| One-to-one replacements | **45** |
| Splits (one withdrawn subcategory, several successors) | **34** — 25 with two successors, 6 with three, 1 with four, 2 with five |
| Widest split | `ID.SC-01` into `GV.RM-05`, `GV.SC-01`, `GV.SC-06`, `GV.SC-09`, `GV.SC-10` |
| Disposition verbs | `Incorporated into` (61), `Moved to` (17), `Moved into` (1) |
| Successors that are categories, not subcategories | `GV.PO`, `GV.RR`, `ID.IM`, `DE.AE` |

Source: `Frameworks/csf2.xlsx`, sheet `CSF 2.0`, counted 2026-08-28.

**Import it as crosswalk edges, not as a field on the concept.** A split is the reason. `ID.AM-06` was replaced by two subcategories, so one flat `previous_ids` property would have to hold a list and could never say anything per replacement. As [crosswalk edges](/crosswalker/concepts/terminology/#crosswalk-edge) it is two ordinary assertions, `superseded_by`, sharing a subject; a merge is N edges sharing an object; and the successor walk that answers "what replaced this control" is the same closure query every other predicate uses.

The bundled `nist-csf-2-withdrawal-lineage` recipe emits exactly that: 127 edges from `nist-csf-1-1:<old id>` to `nist-csf-2:<new id>`, each recording NIST as the mapping provider and preserving NIST's own disposition verb in `lineage_disposition`. The subject side is `nist-csf-1-1` because the withdrawn identifiers are CSF v1.1 identifiers; CSF 2.0 lists them only to record that they are gone. That is what makes the lineage useful after an upgrade: an approval recorded against `nist-csf-1-1:ID.AM-06` in a vault since re-imported at CSF 2.0 has no concept of its own left, and the edges are what turn "this link points at nothing" into "this control was replaced by these two".

**One producer step is required, and it is the only one.** The workbook packs up to five successors into a single cell, and a recipe renders exactly one note per source row, so the 79 marker rows cannot become 127 edge notes on their own. `tools/lineage-from-csf-workbook.ts` does that fan-out and nothing else:

```bash
bun tools/lineage-from-csf-workbook.ts \
  --source Frameworks/csf2.xlsx \
  --out recipes/import/crosswalks/nist-csf-2-withdrawal-lineage.csv
```

It repeats a marker row once per successor and adds one column. It selects no rows, mints no identifiers, and reads no disposition verb; the recipe does all of that, and its `source.where` picks the 127 lineage rows out of the 279 the file carries. The emitted list is committed alongside the recipe, so importing published CSF lineage needs the recipe only. Re-run the tool when NIST publishes a new release.

The tool refuses anything it does not recognise: a marker whose wording is not one of the three verbs above, or a successor that is not a CSF identifier, aborts the run naming the row rather than importing a partial lineage.


## MITRE ATT&CK Enterprise

**Obtain it:** [ATT&CK data and tools](https://attack.mitre.org/resources/attack-data-and-tools/). The bundled recipe reads the Excel export, not the STIX bundle.

**Bundled recipe:** `mitre-attack-technique-flat`, which produces one note per technique or sub-technique.

### Exact binding and result

| Item | Verified value |
|---|---|
| Sheet | `techniques` |
| Header row | Index 0 |
| Rows | **656** |
| Columns | 23 |
| Version compatibility checked | Column set identical between v15.1 and v16.1 |
| Key columns | ID; name; description; tactics; platforms; is sub-technique; url |

Identifier pattern: `T\d{4}(\.\d{3})?`, for example `T1059` and `T1059.001`.

The recipe emits tactics, platforms, and data sources as arrays; adds parent links for sub-techniques; and carries MITRE's notice into every generated note.

### Gotchas

- **Choose the Excel recipe for the Excel file.** A STIX bundle has a different shape and needs another recipe.
- **Citation markers remain inline.** Text such as `(Citation: TechNet How UAC Works)` is part of the exported prose and is preserved.
- **Mitigations are not imported.** They require a join through a separate relationships sheet, which this recipe does not perform.
- **Contributor and date fields are omitted.** Contributor delimiters are ambiguous, and source dates are not normalized ISO values.

## CIS Controls v8.1.2

**Obtain it:** [CIS Controls](https://www.cisecurity.org/controls). Registration is required. Crosswalker does not distribute the workbook.

**Bundled recipes:**

| Recipe | Required row kind | Result |
|---|---|---|
| `cis-controls-v8-flat` | Safeguard rows | 153 safeguard notes |
| `cis-controls-v8-controls` | Control rows | 18 control notes |

### Exact binding

| Item | Verified value |
|---|---|
| Sheet | `Controls v8.1.2` |
| Header row | Index 0 |
| Rows | **171 = 153 safeguards + 18 controls** |
| Columns | 9 |
| Key columns | CIS Control; CIS Safeguard; Title; Description; Asset Type; Security Function; IG1; IG2; IG3 |

Safeguard identifiers follow `\d+\.\d+`, for example `1.1`, `3.5`, and `4.10`.

### Gotchas

> [!danger] Numeric identifier collapse
> The workbook stores safeguard identifiers as numbers. A parser reading raw values turns `4.10` into the float `4.1`, so it collides with safeguard `4.1`. The import then creates 152 distinct safeguard identifiers instead of 153, with no error. Crosswalker reads formatted values to preserve both.

- **The two recipes select opposite halves of one sheet.** The safeguard recipe keeps the 153 rows with a `CIS Safeguard` value; the control recipe keeps the 18 without one. Each declares that predicate itself, so both can be pointed at all 171 rows. A recipe over this sheet that selects neither half creates empty or duplicate paths.
- **The control descriptions are their own row kind.** They are not safeguards and should not be inferred from the safeguard rows.

## CRI Profile v2.2

**Obtain it:** [Cyber Risk Institute Profile](https://cyberriskinstitute.org/the-profile/). Registration is required. Crosswalker does not distribute the workbook.

**Bundled recipe:** `cri-profile-v2-2-flat`, which produces one note for each function, category, subcategory, and diagnostic statement row.

### Exact binding and result

| Item | Verified value |
|---|---|
| Sheet | `CRI Profile v2.2 Structure` |
| Header row | **Index 2**; row 0 is a banner and row 1 is blank |
| Rows | **472**: 7 functions, 28 categories, 119 subcategories, 318 diagnostic statements |
| Columns | 11 |
| Result | 472 notes; `tier_1` through `tier_4` appear only on the 318 diagnostic-statement rows |

### Gotchas

> [!danger] A correct row count can hide the wrong header
> Header index 1 still returns 472 rows, but every column is named `__EMPTY`, `__EMPTY_1`, and so on. Use **index 2** and verify column names, not just the row count.

- **Dots in column names require literal key access.** Older Crosswalker builds split names such as `CRI Profile v2.2 Diagnostic Statement` on every dot, producing 472 bodyless notes without an error. This was fixed in the plugin on 2026-08-26. If CRI notes have empty bodies, update Crosswalker and re-import.
- **Seven rows contain embedded CRLF line endings.** Crosswalker writes LF. Normalize line endings before byte-for-byte content comparisons.
- **Other CRI mapping sheets were not part of the 2026-08-27 verification pass.** Use the publisher's current workbook labels rather than the old v2.0 sheet list previously shown on this page.

## Secure Controls Framework 2026.1

**Obtain it:** [SCF download](https://securecontrolsframework.com/scf-download/). Crosswalker does not distribute the workbook.

**Bundled recipe:** `scf-2026-flat`, which produces one note per SCF control.

### Exact binding and result

| Item | Verified value |
|---|---|
| Sheet | `SCF 2026.1` |
| Header row | Index 0 |
| Rows | **1,468** |
| Columns | **369** |
| Generated body volume | About **9 MB** |

### Gotchas

- **Prune before passing rows through narrow automation bridges.** Enumerating all 369 properties can throw `RangeError: Too many properties to enumerate` in naive tooling. Keep the columns the recipe references.
- **Body volume is the scale pressure.** The 1,468-row count is ordinary; about 9 MB of generated prose is what makes indexing and downstream processing noticeably heavier.
- **`control_weighting` is numeric.** Preserve it as a number so Obsidian Bases can sort and filter it numerically.
