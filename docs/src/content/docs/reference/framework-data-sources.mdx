## Silent-failure checklist

> [!danger] Check these before trusting an import
> These failures can produce plausible row counts, valid-looking notes, or no error at all.
>
> 1. **CIS float collapse:** safeguard identifiers are numeric cells. A raw-value reader turns `4.10` into the float `4.1`, colliding with safeguard `4.1`. One note disappears silently. Crosswalker reads formatted cell values to keep the identifiers distinct.
> 2. **CRI header index:** the CRI v2.2 header is at row **index 2**. Index 1 still returns the correct 472 rows, but names every column `__EMPTY`, so a row-count-only check falsely passes.
> 3. **NIST line counting:** the NIST SP 800-53 CSV has about 2,605 physical lines because control text contains embedded newlines, but it has **1,189 records**. `wc -l` does not measure CSV records.
> 4. **Row selection:** the CSF workbook has 46 banner rows; the two CIS recipes share one sheet containing two row kinds; and the two CPRT recipes encounter 227 non-concept elements. Pointing a recipe at a collection that mixes row kinds is what silently collapses rows onto empty or duplicate paths. Each of those five bundled recipes now declares its own row predicate, so you can point it at the full source collection and skip the manual prefilter that used to be required. A recipe you write yourself still needs one: a source that mixes row kinds and a recipe that does not say which kind it wants is the failure.
> 5. **SCF width and volume:** the SCF workbook is 369 columns wide. Naive automation can throw `RangeError` while enumerating a row. Its practical scale pressure is about 9 MB of generated body text, not its 1,468-row count.

## Stack detail variants

The [framework stack](/crosswalker/getting-started/quick-start/) selects `nist-800-53-r5-nested` and `cri-profile-v2-2-nested` for its NIST 800-53 and CRI slots. Ordinary file recognition continues to propose `nist-800-53-r5-flat` and `cri-profile-v2-2-flat`. The nested NIST variant makes family folders, control folder notes, and enhancement notes; family folders have no concept notes, so family-level mapping endpoints remain unresolved pending a separate identity-safe design. The nested CRI variant makes function, category, and subcategory folder notes and diagnostic-statement notes. Both keep their flat counterpart's source binding, frontmatter, and body projections (source: `recipes/import/nist-800-53-nested.json`, `recipes/import/cri-profile-v2-2-nested.json`).

Choose **Top framework levels as notes** to omit NIST enhancements and CRI diagnostic statements for that run; ATT&CK and CSF are unchanged. This is a row filter, not a rewrite of the bundled recipes (source: `src/import/stack/stack-model.ts` and `src/import/run-recognized-import.ts`). Switching detail on an existing import set is not supported yet. Start a new set for a different detail level; refresh an existing set only with its recorded recipe.

### Referenced frameworks: identifiers without licensed text

A [referenced-framework note](/crosswalker/concepts/terminology/#referenced-framework-note) holds a target identifier from a publisher's crosswalk, not the target framework's title, description or requirements. The private SCF manifest (`scripts/lib/private-scf-manifest.mjs`) pins its selected column names, labels and ontology keys. It selects current base sources rather than every historical edition, implementation group, assessment variant or national overlay. ISO, AICPA, PCI, cloud, industrial, privacy, AI and jurisdictional sources remain distinct; identical local identifiers in different frameworks never merge.

- Existing CSF, SP 800-53 and CIS notes are used where present. ATT&CK resolves only the public Persistence sample; absent techniques are counted and excluded, never replaced by identifier-only notes. This SCF release has no CRI-named column. `CR CMM 2026` is a different source, not an alias for CRI.
- Each distinct source/target pair becomes one mapping using the existing unspecified-relation convention, `skos:relatedMatch`. No exact, broader or narrower relationship is invented. Source assertions, repeated pairs, missing source identifiers, missing endpoints and identifier-only note counts are reported by column.
- The generic `referencedFramework()` accepts a selected column, framework label, pinned ontology key and source-id column. The same adapter accepts normalized CRI Catalog rows; a future catalog integration must retain its declared relationship semantics rather than replacing directional OLIR relations with the unspecified default.
- Ontology keys use the fixed `referencedOntologyKey()` slug rule and are stored literally in the manifest. Non-CURIE characters in identifiers use the engine's injective identity encoding; original identifiers remain the note's `id` and title. Filenames use a separate injective token.
- One muted **Referenced, id only** graph group selects replaceable recipe provenance, not sticky tags or user properties. SCF has its own stable group. SCF notes link directly to referenced notes; those notes link back to the SCF sources. `Start here` reports actual counts and opens the adapted **Frameworks reached by SCF control** Bases query.
- Full-content takeover is deliberate: use the same ontology, original import set, destination and filename mapping. A synthetic real-CLI test (`tests/cli/referenced-framework-takeover.test.ts`) proves unchanged identities and mapping links, preserved user annotations, and replacement of the identifier-only explanation/provenance with full content. Matching an ontology alone does not authorize refresh or relocation. Automatic arbitrary-layout takeover remains outside this slice.

### Resolution and release limits

- Mapping adapters reuse the [stack readers](#stack-mapping-sources), write temporary SSSOM files outside the repository and import them through `cw`. Each external release explicitly uses [set-qualified mapping identities](/crosswalker/development/setup/#build-commands-raw), so overlapping assertions from independent releases coexist. Existing CLI defaults and public demo output do not change.
- Endpoint resolution uses actual note `curie` properties across the vault, never folder names. Formatting normalization is limited to SP 800-53 zero padding / whitespace and CSF single-digit suffix padding. **No CRI version migration is inferred.** The older files' CRI endpoints all resolved as written against the imported 2.2 notes in this verification; this proves identifier presence, not semantic equivalence across releases.
- The public ATT&CK sample is incomplete. Rows without both endpoint notes are excluded and counted by missing subject, missing object or both; blank mapping endpoints and duplicate JSON assertions are reported separately. The catalog logs each absent counterpart sheet instead of pretending to import its mappings.
- Workbook readers preserve displayed identifiers and expand declared merged cells only. They do not generically fill missing mapping endpoints. Subject-tag enrichment is a separate cross-sheet join because the shipped row recipe cannot express that join. Tags assigned by the per-statement sheet are retained even when its tag-list lookup is stale.

### Identifier format

Pattern: `[A-Z]{2}-\d+(\(\d+\))?`

- Family: `AC`, `AU`, `CA`
- Control: `AC-1`, `AC-2`
- Enhancement: `AC-2(1)`, `AC-2(13)`

### Gotchas

- **Do not count records with `wc -l`.** Embedded newlines explain the gap between about 2,605 physical lines and 1,189 CSV records.
- **Preserve enhancement parentheses.** A custom filename transform that strips rather than sanitizes punctuation can make `AC-2(1)` and `AC-2(13)` collide.
- **Clean the related-controls field.** Empty rows can carry `[None]`, and identifiers can have trailing punctuation. Without cleanup, links such as `[[SC-37.]]` and `[[[None]]]` render but do not resolve.
- **No row prefilter is needed** for this lineage: every record represents a control or enhancement.

### Assessment procedures

**Source:** [SP 800-53A Rev. 5 assessment procedures](https://csrc.nist.gov/pubs/sp/800/53/a/r5/final)

Assessment identifiers need normalization before joining to controls:

```text
AC-01_ODP[01]  →  AC-1
Pattern: /^([A-Za-z]+)-0?(\d+)/
```

### Gotchas

- **The workbook mixes banner rows with subcategory rows.** Only rows with a non-empty `Subcategory` are real; the other 46 resolve to empty filenames and collide. The bundled recipe declares that selection itself, so no manual prefilter is needed.
- **The CPRT collection includes 227 non-concept elements** (225 `sort` ordering keys and 2 `party` elements) that must not become concept notes. Both bundled CPRT recipes exclude them by element type, leaving **679** concept elements.
- **Withdrawal markers are real rows, and they carry lineage.** Of 185 subcategory rows, 79 are withdrawal markers naming the CSF 2.0 subcategories that replaced them. If you count only active outcomes, the total is 106. See [Withdrawal lineage](#withdrawal-lineage) below for what the markers look like and how to import them.
- **Merged-cell hierarchy columns are empty on subcategory rows.** The bundled flat recipe derives function and category from the subcategory identifier rather than trusting those cells.
- **Outcome text repeats the identifier.** The bundled flat recipe projects the cell verbatim, prefix included. That is now a deliberate choice rather than a grammar limit: `{Subcategory|regex(:\s*(.+)$)}` recovers everything after the first colon on all 185 rows, but changing the shipped recipe would move its hash and rewrite every already-generated note.
- **Informative References is intentionally omitted.** It contains newline-separated mappings whose labels and identifiers need per-item cleanup before they can become reliable links.

### Withdrawal lineage

CSF 2.0 does not just mark a v1.1 subcategory as gone: it says what replaced it. That statement is machine-readable, but it is written in prose inside the `Subcategory` cell.

```text
ID.AM-06: [Withdrawn: Incorporated into GV.RR-02, GV.SC-02]
ID.GV-03: [Withdrawn: Moved to GV.OC-03]
ID.RM-03: [Withdrawn: Moved into GV.RM-02]
```

| Item | Verified value |
|---|---|
| Withdrawal markers | **79** of the 185 subcategory rows |
| Successor references | **127** across those 79 markers |
| One-to-one replacements | **45** |
| Splits (one withdrawn subcategory, several successors) | **34** — 25 with two successors, 6 with three, 1 with four, 2 with five |
| Widest split | `ID.SC-01` into `GV.RM-05`, `GV.SC-01`, `GV.SC-06`, `GV.SC-09`, `GV.SC-10` |
| Disposition verbs | `Incorporated into` (61), `Moved to` (17), `Moved into` (1) |
| Successors that are categories, not subcategories | `GV.PO`, `GV.RR`, `ID.IM`, `DE.AE` |

Source: `Frameworks/csf2.xlsx`, sheet `CSF 2.0`, counted 2026-08-28.

**Import it as crosswalk edges, not as a field on the concept.** A split is the reason. `ID.AM-06` was replaced by two subcategories, so one flat `previous_ids` property would have to hold a list and could never say anything per replacement. As [crosswalk edges](/crosswalker/concepts/terminology/#crosswalk-edge) it is two ordinary assertions, `superseded_by`, sharing a subject; a merge is N edges sharing an object; and the successor walk that answers "what replaced this control" is the same closure query every other predicate uses.

The bundled `nist-csf-2-withdrawal-lineage` recipe emits exactly that: 127 edges from `nist-csf-1-1:<old id>` to `nist-csf-2:<new id>`, each recording NIST as the mapping provider and preserving NIST's own disposition verb in `lineage_disposition`. The subject side is `nist-csf-1-1` because the withdrawn identifiers are CSF v1.1 identifiers; CSF 2.0 lists them only to record that they are gone. That is what makes the lineage useful after an upgrade: an approval recorded against `nist-csf-1-1:ID.AM-06` in a vault since re-imported at CSF 2.0 has no concept of its own left, and the edges are what turn "this link points at nothing" into "this control was replaced by these two".

**One producer step is required, and it is the only one.** The workbook packs up to five successors into a single cell, and a recipe renders exactly one note per source row, so the 79 marker rows cannot become 127 edge notes on their own. `tools/lineage-from-csf-workbook.ts` does that fan-out and nothing else:

```bash
bun tools/lineage-from-csf-workbook.ts \
  --source Frameworks/csf2.xlsx \
  --out recipes/import/crosswalks/nist-csf-2-withdrawal-lineage.csv
```

It repeats a marker row once per successor and adds one column. It selects no rows, mints no identifiers, and reads no disposition verb; the recipe does all of that, and its `source.where` picks the 127 lineage rows out of the 279 the file carries. The emitted list is committed alongside the recipe, so importing published CSF lineage needs the recipe only. Re-run the tool when NIST publishes a new release.

The tool refuses anything it does not recognise: a marker whose wording is not one of the three verbs above, or a successor that is not a CSF identifier, aborts the run naming the row rather than importing a partial lineage.
