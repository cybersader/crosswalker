Every user action the plugin performs on a vault must also be reachable from `cw`, or have a tracked gap with a reason and a plan. The reverse applies too: a headless action needs a UI or a tracked gap. This is **engine parity (the same action and result), not UI cloning**.

**Status last verified:** 2026-10-30 — verified against `src/main.ts` command registrations, `cli/crosswalker.ts` dispatch, the import wizard, settings, recipe library, mapping review and evidence editor; inventory recorded in `tools/parity/capabilities.ts`.

The UI stays primary. Wizard steps, previews, pickers and navigation need no command line twin; the vault action they produce does. A script, an agent, CI and a person should be able to use the same engine for the [ontology lifecycle](/crosswalker/concepts/ontology-lifecycle/). This makes [schema-as-primitive](/crosswalker/concepts/etl-and-import/) practical without maintaining a second implementation. The [decision record](/crosswalker/agent-context/zz-log/2026-10-30-ui-cli-parity-rule/) captures the owner's direction.

## Current inventory

`tools/parity/capabilities.ts` is the single source of truth. Do not edit the generated region by hand. Command ids are the local ids passed to Obsidian's `addCommand`, without the plugin prefix. Listed flags identify the route to the outcome, not the complete usage syntax; run `bun run cw -- help` for required arguments. Help is an affordance, not a separate vault capability.

## What the gaps mean

A green gate means **every registered action is accounted for**, not that all gaps are closed or that equivalent output has been tested for every action. Outcome-level unit and end-to-end proofs remain necessary. Multiple outcomes may use one verb; for example, `cw export` covers the separate CSV and mapping formats.

The code inventory corrects two assumptions in the initial decision card:

- **Refresh already exists.** `cw import --set` refreshes a chosen set; `cw replay` uses its kept [recipe](/crosswalker/concepts/terminology/) revision. Set listing and deletion are still gaps. The existing UI deletion command is the protected developer test-import reset, not a general-purpose set-management screen.
- **A built-in recipe list is not a saved library.** `cw recipes` lists built-ins only. Reading a recipe file with `cw import --recipe` does not save it into the library.

Typed mapping table import and table-form selection are also tracked gaps: `cw import` dispatches `.sssom.tsv` files, not the plugin's separate typed-table importer, and exposes no storage choice. A configurable wizard default is not a new capability for each toggle: import outcomes represent recipe-controlled naming, hierarchy, properties and links. Runtime-only preferences and developer affordances are recorded as not planned where appropriate, never presented as covered.

## Closure order

1. **Set management:** list identities and safely delete sets. Keep existing refresh and replay paths.
2. **Saved queries and graph colors:** expose the shared builders through `cw`. `demo:build` currently writes these outside `cw`; making the demo plain command line calls removes duplicated orchestration.
3. **Approvals:** expose mapping and evidence review with the same safeguards, not generic property edits.
4. **Recipe library:** save, browse, reuse and share portable recipes through both surfaces.

These are the **UI/CLI parity backlog** under [Deterministic avenues: command line and live demo](/crosswalker/reference/roadmap/#deterministic-avenues-command-line-and-live-demo-near-term). The table's plans reference this order; other gaps follow it or explain why no twin is planned. No new CLI verbs ship in this change.

## Adding or changing a capability

1. Add the UI command or CLI action using the existing shared engine. Inventory wizard and settings vault actions too, even if they have no command id.
2. Add or update an entry in `tools/parity/capabilities.ts`: stable kebab-case id, lifecycle stage, user outcome, actual UI commands or surface, CLI verb and relevant flags. A missing side is `null` and requires `gap.side`, a nonempty reason, and a roadmap plan or an explicit not-planned explanation.
3. Run `bun run parity:write`. It changes only the marked region above, including counts.
4. Run `bun run check:parity` and the relevant behavior tests. Commit the registry and generated table together.

The checker parses TypeScript syntax without running the plugin. It inventories real `addCommand` calls across `src/`, and literal cases in `cli/crosswalker.ts`'s `switch (command)` (`cli/main.ts` is only the process entry). Comments, help examples and unrelated object ids do not count. Dynamic command registrations and changed dispatch shapes fail closed until the inventory logic and its synthetic tests are updated. It checks missing and stale registrations, incomplete gaps, duplicate identities and table drift. Named surfaces and flags are reviewed manually; the gate does not prove they still exist or provide behavioral equivalence.
