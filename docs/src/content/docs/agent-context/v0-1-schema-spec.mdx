## §1 Why this page exists

The [Foundation phase](/crosswalker/reference/roadmap/) intro states: *"The three interconnected schemas (_crosswalker metadata, ImportRecipe, [StewardshipProfile](/crosswalker/agent-context/zz-log/2026-05-01-foundation-commitments-and-followon-research/)) must be designed together — getting any wrong is expensive to fix later."* The [v0.1 stack-pivot](/crosswalker/agent-context/zz-log/2026-05-02-v0-1-initial-stack-pivot/) makes this concrete by committing to a buildable Tier 1 + Tier 2 sidecar architecture.

This page is the **unified v0.1 schema reference**. It distinguishes governing [Schema Contracts](/crosswalker/concepts/terminology/#schema-contract), the artifacts they govern, and derived representations:

1. **Tier 1 Schema Contract** — [`spec/tier1.schema.json`](https://github.com/cybersader/crosswalker/blob/main/spec/tier1.schema.json) governs canonical Tier 1 member-record representations, including `_crosswalker` provenance, concept records, crosswalk assertions, and junction/evidence assertions.
2. **Recipe Schema Contract** — [`spec/recipe.schema.json`](https://github.com/cybersader/crosswalker/blob/main/spec/recipe.schema.json) governs **ImportRecipe**, an intensional Recipe subtype that drives generation but remains outside Tier 1 knowledge.
3. **Tier 1 record shapes** — `_crosswalker` metadata and the junction-note/crosswalk/concept discriminators are member representations within concrete [Knowledge Sets](/crosswalker/concepts/terminology/#knowledge-set). v0.1 does **not** claim a generalized `KnowledgeSet` aggregate schema.
4. **Tier 2 sidecar SQL representation** — a qualified Tier 1 → Tier 2 projection into queryable SQLite. Tier 2 is deletable and recoverable from Tier 1.

[Artifact roles and authority](/crosswalker/concepts/artifact-roles-and-authority/) is the governing conceptual model: Schema Contracts govern; Knowledge Sets are extensional; Recipes are intensional; future Execution Records and Package Manifests are separate administrative envelopes.

The earlier-written [config-schema-design](/crosswalker/agent-context/config-schema-design/) and [constraint-enforcement](/crosswalker/agent-context/constraint-enforcement/) pages stay as background design rationale; this page is the consolidated v0.1 build target.

### Naming history: FrameworkConfig → ImportRecipe

The type now called **`ImportRecipe`** was originally proposed as `FrameworkConfig` in the [config-schema-design](/crosswalker/agent-context/config-schema-design/) page (2026-04). On 2026-05-03 the name was changed for two reasons:

1. **General-ontology positioning.** "Framework" baked the GRC use case into a type that's actually general — any structured ontology (compliance frameworks, biomedical taxonomies, library classifications, custom domain hierarchies) can be imported via this recipe. "Ontology" is the broader term that already pervades the project's vocabulary ([ontology lifecycle](/crosswalker/concepts/ontology-lifecycle/), [ontology evolution](/crosswalker/concepts/ontology-evolution/), ontology diff primitives).
2. **Recipe vs config.** "Config" sounds like *settings*; this artifact is actually a *reusable transformation recipe* applied to a source. A recipe is shareable, version-controlled, and replayable — semantics that "config" doesn't carry.

Companion field renames in `_crosswalker` metadata and junction-note schemas:

- `framework_id` → `ontology_id`
- `framework_version` → `ontology_version`
- `framework` (junction-note field) → `ontology`
- `config_id` (in `_crosswalker`) → `recipe_id`

Folder convention (`Frameworks/...`) is **user-controlled** via `recipe.output.base_path` — examples in this doc still use `Frameworks/NIST-800-53-r5/` because NIST 800-53 *is* a framework and that's the natural choice; non-GRC users would set `base_path` to `Ontologies/`, `Standards/`, `Domain/X/`, etc.

Historical decision logs (`zz-log/`) and research deliverables (`zz-research/`) are **preserved verbatim** with the original `FrameworkConfig` / `framework_id` naming — they are dated decision records, not living spec.

```
   │ ┌────────────────┐ ┌──────────────────┐ ┌─────────────────────┐ │

   ┌──────────────────────────────────────────────────────────────────┐

   │ indexes and closure cache for query acceleration                 │
   └──────────────────────────────────────────────────────────────────┘
```

**Cross-contract and representation invariants** (load-bearing):

- The Recipe Schema Contract governs ImportRecipe; the Tier 1 Schema Contract governs generated member records. Validity in one contract does not imply validity in the other.
- ImportRecipe remains adjacent intensional policy, not Tier 1 ontology/mapping content.
- Every field in the Tier 2 SQL representation must be derivable from Tier 1 frontmatter.
- Every Tier 1 frontmatter field that needs to be queryable in Tier 2 must be a flat scalar or a wikilink (no nested objects, no inline expressions). [Bases-queryable](/crosswalker/concepts/metadata-ecosystem/) constraint.
- Managed ownership is declared: Crosswalker updates only recipe-managed top-level fields plus `_crosswalker`; `user_preserve` fields remain untouched.
- Junction notes are generated member records, but users can edit them; v0.1 generation is non-destructive.
- ImportRecipe may be bundled, imported, instantiated from a template, or edited through the workbench. Its canonical specification is preserved separately from implementation-only `ImportMapping`, `RecipeDocument`, `SavedConfig`, and draft state.

## §3 Tier 1 frontmatter contract (canonical Markdown records)

Tier 1 (the canonical Markdown representation) is governed by [`spec/tier1.schema.json`](https://github.com/cybersader/crosswalker/blob/main/spec/tier1.schema.json). A recipe may manage declared top-level fields, while `user_preserve` fields remain user-owned. Every generated record also carries `_crosswalker` provenance (where the record came from).

### `_crosswalker` provenance block

| Field | Required | Meaning |
|---|---:|---|
| `spec_version` | Yes | Tier 1 contract version used to write the record |
| `source_ref` | Yes | Stable or human-readable source reference. Five properties, none of them individually required, plus `additionalProperties: false` (source: `spec/tier1.schema.json § $defs.provenance_block.properties.source_ref`): `file`, `url`, `curie`, `version`, and `source_hash`, the fingerprint of the source bytes the record was produced from. **What validation actually enforces is `minProperties: 1`** — any single one of the five satisfies it, `version` or `source_hash` alone included. The schema's own description text states a stricter intent, "At least one of file/url/curie required", but that sentence is descriptive and the current contract does not enforce it; do not rely on it when validating third-party records. See [the source-byte subsection](#source-byte-digest-what-source_hash-records) |
| `produced_at` | Yes | ISO 8601 production timestamp |
| `producer` | No | Producer name and version |
| `recipe` | No | Reference to the recipe used for this output. Three optional properties, none required (source: `spec/tier1.schema.json § $defs.provenance_block.properties.recipe`): `id`, the recipe identifier; `hash`, the long-standing effective-target receipt, still typed as a plain string with no pattern — deliberately left permissive so existing records keep validating; and `recipe_document_digest`, added 2026-09-06, strictly `^sha256-[a-f0-9]{64}$` via `$defs.recipe_document_digest`. Nothing in the generation path writes the digest field yet — see [the digest subsection](#recipe-document-digest-two-reference-fields) |
| `import_set` | No | Durable ownership stamp. Five properties, two of them required when the block is present (source: `spec/tier1.schema.json § $defs.provenance_block.properties.import_set`): `id` (required) matches `^iset-[a-z0-9]{6}$`; `scheme` (required) is fixed at mint, closed enum `endpoint-v1` or `set-qualified-v1`; `destination` (optional) records the folder the set was last written to; `ontology` (optional) pins the CURIE prefix the set mints under; `derivation` (optional) pins how the set turns a source row into a CURIE local part, closed enum `filename-stem-v1` or `declared-facts-v1`. See the two subsections below |
| `concept_cid` | No | Content identifier for the declared concept-identity scope; layout and mapping-only defaults do not enter a concept's scope |

This normalized whole-row hash is the only changed/not-changed gate. Absent means the producer computed none, which is not a claim that the content is unchanged |
| `review_groups` | No | Three recipe-driven explanation hashes, all required when the block is present: `wording`, `scope`, and `housekeeping` (source: `spec/tier1.schema.json § $defs.review_group_cids`). They classify a changed `review_cid`; they never replace or narrow the whole-row gate |


#### Source-byte digest: what `source_hash` records

`source_ref.source_hash` (a fingerprint of the bytes a record was produced from) answers exactly one question: **which source bytes made this note?** Its schema definition has not changed and is not new — a plain string, deliberately unpatterned, described as "Hash of the source file at import time. Format: `sha256-{hex}`" (source: `spec/tier1.schema.json § $defs.provenance_block.properties.source_ref.properties.source_hash`). It has always been optional and permissive so that external producers writing valid Tier 1 keep validating; **no schema version, `$id` or pattern moved when the runtime producer described below was added.**

**What produces it today.** Two producers, one of them new:

| Producer | Emits | Notes |
|---|---|---|
| The external fixture CLI | Yes, long-standing | Pre-existing raw-byte provenance; unchanged |
| Native `.xlsx` import in the plugin | Yes, new 2026-09-07 | `sha256-` plus 64 lowercase hex characters over the complete pre-parse workbook payload, computed before any decode (`computeSourceByteDigest()` in `src/generation/hash.ts`) |
| Native CSV, JSON and SSSOM import | No | Unchanged. These do **not** synthesize a digest from decoded text or parsed rows, because a fingerprint of decoded output answers a different question |

The XLSX parse reads its file once and keeps those bytes privately for the life of the join handle it returns, so a declared [`source.joins`](/crosswalker/agent-context/zz-log/2026-08-27-source-contract-delivered/) secondary sheet decodes from the same snapshot rather than a fresh read that could return different bytes. **The guarantee is scoped to one parse, not to a wizard session:** the earlier sheet-name listing is a separate discovery read that takes no snapshot and computes no digest, so what the digest identifies is the bytes behind one import's rows and joins. Rationale and the worked example are in the [XLSX source snapshot log](/crosswalker/agent-context/zz-log/2026-09-07-xlsx-source-snapshot-synthesis/).

**What the field does and does not assert.**

- **Absent means unrecorded, never unchanged.** A native runtime import without a recorded byte digest omits `source_hash`; existing notes and output from external producers may already carry it. A mixed vault is expected, and nothing backfills the field — existing skip, no-op and ownership-preservation rules stay authoritative over any urge to rewrite a note just to populate provenance.
- **It identifies bytes, not selectors.** Sheet choice, header row and filters are not part of it; two imports of one workbook with different settings produce the same digest.
- **It is not a signature and not a replay record.** It proves nothing about who produced the record, does not store the source, does not diagnose drift against a file selected later, and is not the source/run binding that [v0.1.7 Track 2](/crosswalker/reference/roadmap/milestones/v0-1-7-exporters/) still owes.
- **The engine does not verify a caller-supplied value.** `buildProvenance()` in `src/generation/provenance.ts` emits `source_hash` when a truthy value is supplied and omits it otherwise; that function is unchanged. A programmatic producer supplying its own digest is responsible for it identifying the original source bytes from which the accompanying rows were parsed, not a serialization of those rows.

:::caution[Status of the runtime producer]
The XLSX runtime producer is **implemented on an unmerged branch and unreleased**. Its targeted runtime acceptance passed on 2026-09-09: a real import wrote a note whose `source_hash` equalled a host-side digest of the same workbook payload the wizard was handed, and the companion negative control executed — a JSON import wrote a note carrying a nested `source_ref` of `{ file: … }` **with no `source_hash` inside it**. That is the distinction the field draws, and it is narrower than "no provenance": the JSON note still records which file produced it. The XLSX check is a **same-payload digest comparison, not proof of external file authenticity**. **This is a scoped Tier 1 runtime result, not a full-suite, Tier 2 or milestone clearance**: no standalone build or other verification suite was run for it, though the normal E2E `onPrepare` build ran as part of the invocation. The schema contract described above is unchanged and shipped; only the producer is new work. Delivery detail, and the independent review's open qualifications, are in [CHANGELOG.md — Real-Obsidian acceptance rerun](https://github.com/cybersader/crosswalker/blob/main/CHANGELOG.md#real-obsidian-acceptance-rerun-the-six-targeted-declarations-passed-2026-09-09).

#### Recipe-document digest: two reference fields

A **recipe-document digest** (a fingerprint naming one complete recipe revision) answers a question the existing hashes cannot: *which exact revision of this recipe is this?* It is stored in exactly two places, both optional, both new on 2026-09-06:

| Schema | Location | Means |
|---|---|---|
| `spec/recipe.schema.json` (SchemaVer 1.10.0) | `metadata.based_on.recipe_document_digest` | The complete ancestor recipe named by `based_on.recipe` |
| `spec/tier1.schema.json` (SchemaVer 1.4.0) | `_crosswalker.recipe.recipe_document_digest`, inside `$defs.provenance_block.properties.recipe` | The complete recipe referenced by that note's provenance |

Both accept only `^sha256-[a-f0-9]{64}$` through a local `$defs.recipe_document_digest` in each schema. Both are optional, so recipes and notes written before this addition still validate, and neither schema `$id` changed.

**Normalized input, and what that includes.** The digest is computed by `computeRecipeDocumentDigest(recipe)` in `src/generation/hash.ts`, which is `sha256-` plus the SHA-256 of `canonicalStringify()` over the whole recipe object. **It neither validates nor normalizes what it is given**: its precondition is a validated canonical recipe already put through `normalizeRecipe()` (`src/import/recipe-document.ts § normalizeRecipe`). Any external producer computing this digest must therefore do both steps first — passing raw recipe JSON straight in yields a digest for a different object than the one Crosswalker would identify. Keeping normalization on the caller also keeps the module graph acyclic — `recipe-document.ts` imports `hash.ts`, never the reverse.

Because normalization runs first, the digest covers the defaults `normalizeRecipe()` supplies: `spec_version`, `target.linkStyle`, the folder `variadic` defaults (`segment`, `drop_last`, `max_depth`, `on_overflow`), and the `also_emit.body` defaults (`position`, `format`, `omit_if_empty`, and `heading_depth` for `section` entries) — sourced from that function. The practical consequence for external producers: **an omitted default and an explicitly written equivalent default identify the same revision and digest identically.** This is a digest of a normalized canonical recipe, not of arbitrary raw recipe JSON, and object key order and input-file whitespace do not affect it while array order does.

**How it differs from the existing recipe hash.** `computeRecipeHash()` hashes a deliberately reduced slice: `layout`, `also_emit`, `enrichment`, `auto_heading`, `target.crosswalks`, `source.nest`, `source.where`, and `source.joins` (source: `src/generation/hash.ts § recipeHashCanonicalInput`) because it answers "did anything that changes output behavior change?" The document digest covers the whole recipe, so a changed recipe id, title, or ancestry reference changes the digest while leaving the effective-target hash fixed. Both meanings, and every value already written under them, are unchanged by this addition.

**No self-field and no stripping.** Digests live on references to *other* documents, so a recipe never carries its own digest: an own-digest property on recipe metadata is rejected by the closed metadata schema. Nothing is excluded before hashing either — an ancestor digest string already present in a recipe is ordinary document content and participates in that recipe's digest, as does any similarly named key inside an opaque block.

**What emits it today.** Only the existing fork path: when `patchRecipeDocument()` customizes a recognized recipe and writes `metadata.based_on`, it records the digest of the normalized original *before* the descendant's edits (`src/import/recipe-document.ts § patchRecipeDocument`). Fresh documents still get no ancestry, and a no-op patch mints nothing. **The Tier 1 field is contract only**: no generation path stamps `_crosswalker.recipe.recipe_document_digest` yet, and this slice adds no recipe storage, recipe-library UI, source retention, or replay execution.

#### What is pinned to the set, and why

`scheme`, `destination`, `ontology` and `derivation` are all recorded on the set rather than recomputed per run. They exist because the same question - *where does this import already live, and under what names?* - was previously answered by looking at the vault, and looking at the vault answers a different question: it describes an address, not an owner.

| Property | Required | Pinned when | What a run does with it |
|---|---:|---|---|
| `id` | Yes | Minted once, crypto-random and meaningless | Names the set. A refresh reuses it; nothing derives it from a recipe, a destination, or a source, because all three legitimately change |
| `scheme` | Yes | Mint | Fixes crosswalk-assertion identity for the life of the set. A refresh may not change it |
| `destination` | No | Re-stamped every run | A hint about where the set lives, so a refresh does not have to infer a root from a derived default. Never authority: nothing updates it when a user renames the folder in the file explorer, so a reader re-validates it against the set's actual note paths before writing there |
| `ontology` | No | Mint; a legacy set is pinned on its first refresh to the prefix its own notes already carry | The CURIE prefix a refresh mints under. A run uses the pin in preference to the ontology its own recipe implies |
| `derivation` | No | Mint | Which rule turns a source row into a CURIE local part. A run uses the set's pin, never this version's current rule |

`ontology` prevents a specific and total failure: a refresh that recomputes the ontology from its own recipe can land on a different answer than the one the set's notes carry - a renamed saved config, a differently named export file - and every CURIE it then writes matches none of the notes it owns. The run writes a second copy of the whole import beside the first and reports every original as an orphan. Absent on notes written before the pin existed, which is why a legacy set is pinned from its own notes rather than from the run.

`derivation` prevents the same failure from the opposite direction, and it is why the identity rule could be corrected at all. The rule shipped since v0.1.0 builds a concept's CURIE local part out of its leaf filename stem, passed through the filesystem sanitizer, so `AC 2`, `AC-2` and `AC/2` all collapse onto one identity and even a declared `curie` column gets rewritten. Correcting that rule in place would give every note in every existing vault a new CURIE, and the next refresh would recognise none of them. So the rule is pinned instead: a set stamped `filename-stem-v1`, or carrying no stamp at all, keeps the legacy derivation byte-exact forever, and only a newly minted set derives under `declared-facts-v1` (source: `src/generation/import-set.ts § derivationOf`).

`declared-facts-v1` consults the source's own identity columns first, in the order `curie`, `id`, `subject_id`, `control_id`, `code`, and falls back to the filename stem only when none is present. A declared `curie` outside the CURIE charset is refused for that row by name rather than rewritten. Any sanitization that does happen is injective: a value already inside the charset passes through unchanged, and any other value becomes `<safe form>..<short digest of the exact raw value>`, so two distinct source values can never produce one CURIE (source: `src/generation/curie.ts § injectiveCurieLocalPart`).

Independently of any pin, a single run refuses to produce one CURIE twice. The second row to claim an identity is reported by name alongside the row that claimed it first, and nothing is written for it. That guard changes no identity, so it applies to legacy sets as well as new ones (source: `src/generation/generation-engine.ts § duplicateCurieMessage`).

Neither optional property is an ownership decision. Ownership is carried only by `id`, and the set a run writes under is chosen by the caller, never inferred by the engine from what happens to sit in the destination folder (source: `src/generation/import-set.ts § resolveImportSet`).

#### Crosswalk assertion identity

Crosswalk assertion identity (the stable name of one mapping note) follows the owning set's fixed scheme. Both values and forms below are defined by `spec/tier1.schema.json § $defs.provenance_block.properties.import_set.properties.scheme`:

- `endpoint-v1`: `cw-<sanitized-subject>-<sanitized-object>`. This is the original form and remains byte-identical on refresh.
- `set-qualified-v1`: `cwset-<import-set-id>-<sanitized-subject>-<sanitized-object>`. The `cwset-` marker makes the form visibly distinct; the minted set id lets equal endpoint pairs in different import sets coexist. Row order and mapping-set metadata do not enter either form.

Endpoint sanitization follows the set's `derivation` pin for the same reason the concept rule does: under `filename-stem-v1` the original many-to-one form is reproduced byte-for-byte, and only a set minted under `declared-facts-v1` sanitizes endpoints injectively (source: `src/import/sssom-importer.ts § sssomEdgeCurie`).

A refresh always reuses the stored scheme. Choosing coexistence mints a new import set whose assertions use `set-qualified-v1`; no existing note is migrated, moved, or re-identified. See the [import-set ownership decision](/crosswalker/agent-context/zz-log/2026-08-21-import-set-ownership/#how-this-dissolves-release-isolation-rather-than-mitigating-it).

All six 2026-08-21 additions are optional at their containing-record boundary: `parent_curie`, `subject_curie`, `object_curie`, `mapping_set_id`, `predicate_modifier`, and `_crosswalker.import_set`. ## §4 Recipe Schema Contract and ImportRecipe specification

ImportRecipe is a concrete [Recipe](/crosswalker/concepts/terminology/#recipe) subtype: a portable, machine-evaluable declaration of intended source-to-Tier-1 behavior. It is governed by the Recipe Schema Contract and sits adjacent to generation; it is not embedded inside the Tier 1 Knowledge Set it helps produce.

| Recipe role | Meaning in v0.1 |
|---|---|
| **Specification** | The canonical ImportRecipe JSON governed by `spec/recipe.schema.json`. |
| **Template** | Parameterized/default policy, such as a Shape Preset, used to instantiate or initialize a specification/mapping. |
| **Binding** | A Recipe reference plus concrete source identity and selected parameters. |
| **Execution** | One application of a bound Recipe. Verified run facts belong in a later separate Execution Record, not in mutable Recipe intent. |

:::tip[Current machine-readable contract — verified 2026-08-21]
The authoritative v0.1 contract is [`spec/recipe.schema.json`](https://github.com/cybersader/crosswalker/blob/main/spec/recipe.schema.json), summarized in the [portable-recipe fidelity synthesis](/crosswalker/agent-context/zz-log/2026-07-21-portable-import-recipe-fidelity-synthesis/). It uses the settled closed grammar (`folder | file | heading | tag | wikilink`) plus `also_emit`, enrichment, graph edges, and optional query declarations.

The active import workbench now retains the full validated canonical recipe through a lossless `RecipeDocument` boundary. This is **internal/in-memory fidelity**, not yet a durable user recipe library: save/open/export/share UI under `_crosswalker/recipes/import/` remains deferred.
:::

Current additive fields include:

- optional display metadata and structured `metadata.based_on` ancestry, which since 2026-09-06 may also carry `recipe_document_digest`, a strict digest of the complete normalized ancestor recipe (see [the digest subsection](#recipe-document-digest-two-reference-fields) for its input contract and how it differs from the effective-target hash);
- optional `source.version` as compatibility metadata, never stronger than verified run provenance;
- ordered `target.also_emit.body` projections (`append | section` × `text | code | quote | list`);
- typed managed scalar coercion through the closed `number` template filter;
- omission-safe identity templates through first-position `optional` and empty-safe `curie-prefix(prefix)` controls;
- deterministic normalized equality and canonical JSON serialization;
- four validation layers: JSON Schema, recipe semantics, source compatibility, and editable-model portability.

:::caution[Historical design sketch below]
The TypeScript shape and YAML example below predate the May 2026 primitive-grounded recipe decision and are retained as naming/design history. They are **not** the current serialized schema. Read the [Ch 20 synthesis](/crosswalker/agent-context/zz-log/2026-05-03-import-primitive-formal-foundation-synthesis/), [Ch 22 target-structure synthesis](/crosswalker/agent-context/zz-log/2026-05-04-target-structure-synthesis/), and machine-readable schema before implementing against this section.
:::

An ImportRecipe is a portable, deterministic instruction artifact. Bundled recipes currently drive recognition and generation; persistent user-authored recipe-file lifecycle is the next UI/storage slice.

### §4.5 Recipe `query:` block (added v0.1.6 — SchemaVer 1.1.0; additive)

Per [Ch 31 schema design](/crosswalker/agent-context/zz-research/2026-05-08-challenge-31-deliverable-a-shape-dispatched-data-only/) + [Ch 36 compositional language stack](/crosswalker/agent-context/zz-research/2026-05-09-challenge-36-query-language-rerun/), v0.1.6 added an optional `query:` block to the recipe schema. Recipes can now declare WHAT to query (axes, edges, aggregation) without writing SQL — the engine compiles the declared block to SQL recursive CTEs against the Tier 2 sqlite-wasm cache.

**Backward compatibility**: existing recipes WITHOUT `query:` continue to validate. The bump is purely additive (SchemaVer ADDITION); SchemaVer URI did NOT bump (`https://crosswalker.dev/spec/recipe.schema.json` stays).

**Eight Layer A query verbs** (per [Ch 29 adversarial validation](/crosswalker/agent-context/zz-research/2026-05-09-challenge-29-ontology-web-query-verbs-validation/)): `filter / traverse / bind / project / aggregate / anti-join / set-op / diff`. Closure folded into parameterized `traverse(depth=*, transitive=true)`. Pivot demoted to Layer B (presentation, not value-producing).

**Six view shapes** (per [Ch 30 view shape taxonomy](/crosswalker/agent-context/zz-research/2026-05-09-challenge-30-view-shape-taxonomy/)): `table / list / pivot / graph / hierarchy / timeline`. v0.1 first-class catalog: Pivot (custom Bases view `crosswalkerPivot`) + Table/List/Cards (Bases-native consumed) + Hierarchy (graduates v0.1.7-v0.1.8). Graph + Timeline schema-declared; renderers ship v0.2+.

**Top-level query block shape:**

### §4.6 Layout-entry `variadic` block (added 2026-07-05 — SchemaVer 1.2.0; additive)

A fixed layout lists its folder levels ahead of time — one `layout_entry` per level. Ragged ids carry a **different number of pieces per row** (ATT&CK `T1055` vs `T1055.011`; any parent/child id family), so no fixed list fits every row — the result was a flat dump. A folder `layout_entry` can now carry an optional **`variadic`** block that explodes the entry's rendered scalar *after* templating (templates stay scalar — one value in, one value out) into a **variable number of folder levels**.

**Backward compatibility**: purely additive (SchemaVer ADDITION). Recipes WITHOUT `variadic` validate and render byte-identically. The spec URI did NOT bump (`https://crosswalker.dev/spec/recipe.schema.json` stays). `variadic` is schema-constrained (layout_entry `allOf` if/then) to `mechanism: "folder"` only — heading/tag variants are deferred.

**Fields:**

| Field | Type | Default | Meaning |
|---|---|---|---|
| `delimiter` | string (required) | — | What the rendered scalar is split on (e.g. `.` for ATT&CK ids). |
| `segment` | `prefix` \| `part` | `prefix` | Folder-name shape. `prefix`: cumulative prefixes joined by the delimiter (`X.Y.Z` → `X`, `X.Y`) — globally-unique, CSF-convention. `part`: raw pieces (`X.Y.Z` → `X`, `Y`). |
| `drop_last` | boolean | `true` | Drop the leaf piece before building folders — the `file` entry names it with the full id anyway. |
| `max_depth` | integer ≥ 1 | `6` | Safety cap on folder levels produced. |
| `on_overflow` | `truncate` \| `error` | `truncate` | Past `max_depth`: `truncate` keeps the first `max_depth` + records a `variadic-overflow-truncated` deviation note (no data loss — full id is in the filename); `error` fails the render. |

**Semantics** (exact): render `template` → scalar → split on `delimiter` (empty pieces dropped, each → a `folder-level-skipped` note) → if `drop_last`, drop the final piece → build segments per `segment` mode → cap at `max_depth` → append each as a folder level (same path as fixed folders). Zero segments (a top-level id) is normal, not a deviation. Deterministic: segments derive only from the row's own value.

**Example** (ATT&CK technique nesting — `T1055` and `T1055.011` from one recipe):

```yaml
layout:
  - level: root
    mechanism: folder
    template: Techniques
  - level: technique
    mechanism: folder
    template: "{external_id}"
    variadic:
      delimiter: "."
      segment: prefix     # T1055.011 → parent folder T1055
      drop_last: true     # leaf piece belongs to the file
      max_depth: 6
      on_overflow: truncate
  - level: technique
    mechanism: file
    template: "{external_id}.md"
```

`T1055` → `Techniques/T1055.md` (no parent folder); `T1055.011` → `Techniques/T1055/T1055.011.md`.

**Scope**: recipe-only in this round — the import wizard doesn't yet propose or edit `variadic` (planned follow-up: detect the ragged-id signature — a delimiter appearing in ~20–79% of rows — and offer variable-depth nesting). The full folder-note convention (`T1055` *becoming* the `T1055/` container as `T1055/T1055.md`) is a separate batch-scoped post-pass still under design.

### §4.7 `also_emit.frontmatter.managed_links` (added 2026-07-10 — SchemaVer 1.3.0; additive)

Single-value links live in `managed` as a scalar `"[[…]]"` string (`parent: "[[T1078]]"`). A **multi-value** link column — a cell holding several ids (`Related Controls: "AC-2, AC-3, PM-9"`) — needs a YAML **array** of wikilinks so each id is an indexable graph edge, not one dead `[[AC-2, AC-3, PM-9]]` string. `managed_links` is that region.

Each key maps to `{ template, split? }`. render() renders `template` to a scalar, splits it on `split` (default comma + semicolon), wraps each non-empty trimmed piece in `[[…]]`, and emits the key as an array. An empty cell omits the key entirely (an empty managed array would still clobber a user value on re-import). Regenerated wholesale on re-import (managed, not unioned).

**Backward compatibility**: purely additive (SchemaVer ADDITION). Recipes WITHOUT `managed_links` validate unchanged. Spec URI unchanged.

```yaml
also_emit:
  frontmatter:
    managed_links:
      related:
        template: "{Related Controls}"   # bare cell value — render() wikilinks each piece
        split: [",", ";"]                 # optional; this is the default
```

`Related Controls: "AC-2, AC-3, PM-9"` → `related: ["[[AC-2]]", "[[AC-3]]", "[[PM-9]]"]`.

### §4.8 `target.enrichment` block (Pass 1.5; added 2026-07-10 — SchemaVer 1.3.0; additive)

`render()` is per-row pure (Pass 1, hashable). Four artifacts need **cross-row** knowledge, so an optional **batch-scope enrichment pass** runs *after* every row renders (`src/generation/enrich.ts`): children lists on parents, materialized facet hub notes, honest edge stats, and (reserved) folder-note placement. It never touches `render()`; determinism holds at batch level — every derived list is sorted by curie, hubs by path, so input order never leaks.

**Backward compatibility**: purely additive. Recipes WITHOUT `enrichment` emit nothing new and validate unchanged. Spec URI unchanged.

**Fields:**

| Field | Type | Default | Meaning |
|---|---|---|---|
| `children_lists` | boolean | `false` | Each parent note gains a managed `children` array of wikilinks to its direct children (derived from the same parent relation the parent link uses), sorted by child curie. Fully managed — regenerated wholesale on re-import (user extras inside the array are not preserved; `user_preserve` covers *separate* keys). |
| `facet_notes` | `none` \| `tags-only` \| `notes` | `none` | `none`: nothing beyond per-note facet tags. `tags-only`: facet tags only, no hub notes. `notes`: one synthetic hub note per facet **value** with a managed `members` list (sorted by curie), `kind: facet`, the facet tag, and an H1 body; user prose below the H1 survives re-import. Hubs materialize only for values with ≥2 members. |
| `parent_note` | `sibling` \| `folder-note` | `sibling` | Where a concept that is also a parent lives. `sibling`: `X.md` beside `X/`. `folder-note`: `X/X.md` — the batch enrichment pass relocates evidence-based (only parents whose children actually nest under their folder), resolves re-import write targets by curie so no duplicates arise, and relocates back symmetrically when set to `sibling` again. Streamed sources fall back to sibling with a deviation note (eager batch required). |
| `hub_note_folder` | string | *(output root)* | Optional vault-relative folder for materialized facet hub notes. |
| `level_hubs` | `none` \| `notes` | `none` | Added SchemaVer 1.4.0 (§4.9). Hierarchy hub/MOC index notes — one per folder level. |
| `waypoint_marker` | boolean | `false` | Added SchemaVer 1.4.0 (§4.9). Opt-in `%% Waypoint %%` marker on generated folder-note/hub notes. |

**Stats**: `GenerationResult.edgeCount` = parent links + children entries + facet-hub member entries + level-hub child-link entries — the review screen's "K graph edges" line (a run shipping 0 edges is a visible warning, not a silent dead graph).

**Preset defaults** (stamped by `instantiate` onto `ImportMapping.enrichment`, then serialized to `target.enrichment`): `browsable-framework` → `children_lists: true`, `facet_notes: "notes"`, `level_hubs: "notes"`. The hyperconnected default IS the default.

```yaml

    children_lists: true
    facet_notes: notes
    parent_note: sibling
    level_hubs: notes
```

**Scope**: recipe + preset land here; the workbench Connections-card UI knobs and the review-screen edge count are wired (§4.9 for the level-hubs/Waypoint-marker round). Folder-note relocation (step 2 of the design) is implemented in `src/generation/enrich.ts`.

### §4.9 `target.enrichment.level_hubs` + `waypoint_marker` (added 2026-07-11 — SchemaVer 1.4.0; additive)

Closes the [ICSB emitter-controls gap audit](/crosswalker/agent-context/zz-log/2026-07-11-shape-workbench-architecture-synthesis/#3-the-connectedness-mandate--vaults-must-be-graphs-not-filing-cabinets)'s #1-priority gap: Crosswalker had facet hub notes (value-grouping) but no hierarchy-*level* index/MOC concept, unlike the ICSB pipeline's `hubs.*` (Home + per-level MOCs, derived from the canonical model). Delivery detail (folder-note-as-default, per-import root folders, the review screen's exact-count plan) is in [`CHANGELOG.md` "Frameworks arrive furnished"](https://github.com/cybersader/crosswalker/blob/main/CHANGELOG.md#frameworks-arrive-furnished-2026-07-11-third-batch), not restated here.

**`level_hubs: 'notes'`** — every FOLDER level in the generated structure gets an index note, derived from the batch's own rendered note paths (never a filesystem scan):

- **Hosted**: when a folder's own concept note already exists in the batch (sibling `X.md` beside `X/`, or folder-note `X/X.md` — basename is the only identity that matters, since links in this codebase are basename-only), that note gains a managed body **"Contents"** section listing the folder's direct children (subfolders' hub identities + sibling notes, sorted by curie, as `[[wikilinks]]`).
- **Synthetic**: a folder with no such note (a pure structural grouping folder, or the per-import root) gets a brand-new hub note (`kind: 'hub'`, curie `<ontology>:hub/<folder-path-slug>`) at `<folder>/<folder>.md`.
- **Root hub**: the per-import root folder (`GenerationOptions.basePath`) gets a hub too, named after the folder — the import's "home" note.
- Re-import safe: the managed section is delimited by HTML-comment markers and stripped-and-reappended on regeneration (same discipline as `facet_notes`'s H1 split) — user prose elsewhere in the note survives.
- Default `'notes'` on the `browsable-framework` preset (the connectedness mandate — [shape-workbench synthesis §3](/crosswalker/agent-context/zz-log/2026-07-11-shape-workbench-architecture-synthesis/#3-the-connectedness-mandate--vaults-must-be-graphs-not-filing-cabinets)).

**`waypoint_marker: true`** — additionally appends the `%% Waypoint %%` trigger comment to every folder-note/hub note this import generates, so the [Waypoint community plugin](https://github.com/IdreesInc/Waypoint) can *also* track notes a user later adds to that folder by hand. Idempotent (never duplicates or strips a `%% Begin Waypoint %%` block Waypoint has already expanded). Additive, not a replacement — Crosswalker's own generated section stays the primary, always-on mechanism (Waypoint's directory-scan approach can't reconstruct the curated, edge-derived grouping Crosswalker's own model produces). Default `false`; the workbench only offers the toggle when a Waypoint-style plugin is detected enabled.

**Backward compatibility**: purely additive (SchemaVer ADDITION). Recipes without these keys validate and render unchanged. Spec URI did NOT bump.

### §4.10 `source.where` row predicate (added 2026-08-27 — SchemaVer 1.9.0; additive)

The first declaration on `source` that shapes the **collection** rather than a value. Per the [Ch 46 transform-shapes framing](/crosswalker/agent-context/zz-log/2026-08-27-transform-shapes-framing-synthesis/): value-shaping (literal keys, per-item mapping, substrings) stays in templates, which already ship it; deciding **which rows exist, and what a row is** extends the source contract instead.

```jsonc
"source": {
  "ontology": "nist-csf-2",
  "levels": ["subcategory"],
  "where": "Subcategory != ''"
}
```

| Property | Value |
|---|---|
| Type | `string`, `minLength: 1`, `maxLength: 512` (source: `spec/recipe.schema.json` § `source.where`) |
| Language | JSONata, restricted to a closed subset (below) |
| Evaluated against | one source row, exactly as the parser produced it. Spreadsheet cells are strings, so numeric intent must be explicit: `$number(count) > 5`, never `count > 5` |
| Position in the pipeline | `where` → identity → CURIE mint → `concept_cid` → `render()` → Tier 1 validate → write. **Spec-owned, never recipe-owned** |
| Recipe hash | participates, because it changes which notes exist. A recipe omitting it hashes byte-identically to its pre-1.9.0 self |
| Absent | every row becomes a note, exactly as before |

**Permitted subset** (source: `src/source/expression.ts` § `PERMITTED_FUNCTIONS` and the AST walk): field references (bare, backtick-quoted, dotted), string/number/`true`/`false`/`null` literals, array literals, `=` `!=` `<` `<=` `>` `>=`, `in`, `and`, `or`, `&`, grouping parentheses, and 7 functions — `$not` `$exists` `$trim` `$lowercase` `$uppercase` `$string` `$number`.

**Rejected at preflight, by name**: regular expressions and every regex-taking function, lambdas and the higher-order functions that need them, `$eval` / `$lookup` / `$merge` / `$$`, the `~>` chain, `^(...)` sort, `{...}` object constructors, `**` descendants, conditionals, multi-expression blocks, and `:=`. Regex is the load-bearing ban: JavaScript regex and Python `re` disagree, and a producer in another language must be able to evaluate the same predicate and get the same rows.

**The loudness contract** is the reason this declaration is worth a schema change rather than a preprocessing step. Three guards, because one is measurably not enough:

| Guard | Catches | When |
|---|---|---|
| Result must be a strict boolean | `where: "Subcategory"` (returns `''`), `where: "Typo"` (returns nothing), any non-predicate | per row |
| Every referenced name exists in the collection | `Typo != ''` — the case the boolean check cannot see | preflight, before any write |
| Admitting zero rows from a non-empty source | a correct column compared against a literal that never occurs | end of stream, before any write has happened |

The middle guard exists because of a measured fact: JSONata's comparison operators absorb an undefined operand, so a typo'd column name returns a perfectly good boolean `false` for **every** row. A return-type check passes it, the import admits nothing, and nothing is reported. The rule the guard encodes is the same one the join design states for keys: *absence of a field on a row is data; absence of a field from the collection is a defect.* Heterogeneous JSON is why the check is a union over the collection rather than a per-row requirement.

A per-row failure **aborts the run**. It never skips the row: a skip that logs a warning is still a vault that quietly lost rows.

**Cross-runtime behaviour is pinned as data**, not prose: [`spec/conformance/source-expressions.json`](https://github.com/cybersader/crosswalker/blob/main/spec/conformance/source-expressions.json) records what every permitted construct evaluates to, including the undefined-absorption case above, so a Python producer can be checked against the same file the plugin runs.

**Backward compatibility**: purely additive (SchemaVer ADDITION). Recipes without the key validate, render, and hash unchanged. Spec URI did NOT bump.

### §4.11 `source.joins` keyed lookup enrichment (added 2026-08-27 — SchemaVer 1.9.0; additive)

The second collection-shaping declaration, and the one that decides **what a row is**. Keyed lookup enrichment only: one primary stream plus N independent, bounded lookup indexes. Not relational algebra.

```jsonc
"source": {
  "ontology": "mitre-attack",
  "levels": ["technique"],
  "joins": {
    "mitigations": {
      "from": { "sheet": "relationships", "where": "`mapping type` = 'mitigates'" },
      "on":   { "primary": "ID", "secondary": "`source ID`" },
      "cardinality": "many",
      "select": ["target ID"]
    }
  }
}
```

The object key is the **alias**, constrained to `^[a-z][a-z0-9_]*$` so it is addressable as a bare template segment with no quoting (source: `spec/recipe.schema.json` § `source.joins.propertyNames`).

| Field | Contract |
|---|---|
| `from.sheet` + optional `from.header_row` | another sheet of the **same workbook**. XOR with `iterator` |
| `from.iterator` | a sibling array of the **same JSON document**, same closed iterator grammar as the primary |
| `from.where` | optional predicate over the **secondary** rows, with exactly the §4.10 contract: same subset, same three guards, same errors. Fixed depth — there is no nested `joins` |
| `on.primary` / `on.secondary` | key expressions, same restricted subset, normalized identically with a trimmed string coercion. Composite keys use `&` |
| `cardinality` | **required, no default.** `"first"` does not exist |
| `select` | optional field subset for `one`; **required and exactly one field** for `many` |

**Both secondary forms live inside the same source bytes.** The `source` block's own scope excludes where the bytes come from, so a join naming a second file would break that rule and single-file portability with it. A CSV source is one collection and has nothing to name: declaring a join over one is refused with the format reason.

**Cardinality is an assertion about the data, not a preference** (source: `src/source/joins.ts`):

| | zero matches | one match | two or more |
|---|---|---|---|
| `"one"` | alias absent from the row | alias = the matched row, or the `select` subset of it | error naming row, alias, key and count |
| `"many"` | alias absent from the row | list of length 1 | list, in **secondary-collection order** |

Zero matches leaves the alias **absent** rather than empty in both modes, so the existing `|optional` filter handles a miss identically either way. A single match under `"many"` stays a list, because output shape must never depend on how many rows happened to match.

`"many"` binds a **list of scalars**, never a list of objects, and that is a deliberate consequence of the frozen template grammar: path traversal does not lift over arrays (source: `src/render/template.ts`), so a list of objects would require extending the grammar. Instead, a `many` list lands directly in `also_emit.frontmatter.managed` as a YAML array, in `managed_links`, or in a body projection with `format: "list"`.

**Collision policy: never shadow, never merge, never auto-rename.** A joined row gains exactly **one** key — the alias — and its value is the match. Nothing enters the primary row's own namespace, so a secondary column can never overwrite a primary one. An alias equal to an existing column, or to a reserved render-scope name, is refused at preflight. The consequence is the point: `source.joins` requires **zero** template-grammar change, because the alias is an ordinary nested value reached by the dotted traversal and the `['literal key']` quoting that already shipped in SchemaVer 1.7.0 — `{mitigation.['Mitigation Name']}` composes at any depth.

**Loudness, mirroring §4.10**: a key expression that yields nothing, an empty string after trimming, or a non-scalar is an error naming the row. **No match is not an error** — absence of a relation is data, absence of the key is a defect. A secondary collection that is empty, or that `from.where` narrows to nothing, is an error: an index that can never match is a defect.

**Order in the pipeline**: `where` → `joins` → identity → CURIE mint → `concept_cid` → `render()`. `where` runs first so it stays a pure function of the source row, so a discarded row costs no lookup, and so inner-join semantics cannot arrive through `where: "$exists(alias)"` — at the time `where` runs, no alias exists, and the reference preflight rejects the name. A joined value therefore participates in `concept_cid`, which is correct: the alias is part of what the concept asserts.

**Streaming and cost**: the primary collection is still consumed row by row; only the secondary is materialized. Measured against ATT&CK's `relationships` at 18,570 rows, the index builds in ~25 ms, and a 200,000-row primary import against it never holds more than one primary row at a time. Retained memory is a function of the secondary only.

**Two-hop is out of scope, permanently.** ATT&CK's mitigation *prose* lives two hops away (`technique → relationships → mitigations`), and hop 2's key depends on hop 1's result set — a join composing with a join, which is the relational algebra this design excludes by name. A technique note gains mitigation **identifiers**; names and prose are producer work. An honest half-close beats a silent one.

**Backward compatibility**: purely additive (SchemaVer ADDITION). Recipes without the key validate, render, and hash unchanged. Spec URI did NOT bump.

### §4.12 Delimiter-set template filters `part` / `prefix` (added 2026-09-15 — SchemaVer 1.11.0; additive)

`$defs/template` only; no structural key changes (source: `spec/recipe.schema.json` `$comment` history line). Three filter forms join the FILTERS list (source: `src/render/template.ts` `FILTERS`), all splitting on **any single character** of a delimiter set instead of one fixed delimiter:

| Filter | Result | `GV.OC-01.01` with set `.-` |
|---|---|---|
| `part(delimiters,index)` | the 0-based non-empty trimmed piece; an index past the last piece is empty with render note `part-index-missing` | index 2 → `01` |
| `part(delimiters)` | the list of non-empty trimmed pieces, like `split(delimiter)` | → `GV`, `OC`, `01`, `01` |
| `prefix(delimiters,index)` | the **original** value truncated right after the indexed piece, original delimiters kept | index 2 → `GV.OC-01` |

Why a set: mixed-delimiter identifiers (CSF 2.0 `GV.OC-01.01`, CRI Profile ids) carry a hierarchy in one column with more than one separator, and `split(d,n)` can only see one of them. `prefix` is what a cumulative folder path needs: each level's name is the id truncated at that level, delimiters intact, so `GV`, `GV.OC`, `GV.OC-01` nest without a join rule.

Where they are legal: anywhere a template scalar with `split(X,0)` is legal today, which in practice means the structural templates on folder and naming surfaces (layout `folder`/`file`/`tag`/`heading`/`link` templates and `LevelRule`-derived names). They are `$defs/template` filters, so they are not confined to one mechanism; they are simply not list-projection filters like `join` (source: `src/render/template.ts` `FILTERS` and `src/import/mapping/serialize.ts` `buildName`, which emits them for level names). The delimiter set itself comes from the mapping model's `LevelRule.delimiters` (source: `src/import/mapping/types.ts`; the earlier note in this section cites it).

Lexing follows the SchemaVer 1.7.0 rules: the delimiter set is one filter argument, so a set containing `,` `)` `|` or `\` is written `\,` `\)` `\|` `\\`. The index is taken greedily off the decoded argument, so `part(\,;,0)` is a set of `,` and `;` with index 0.

On the mapping side (source: `src/import/mapping/types.ts` `LevelRule`), a level carries `delimiters` (the set) beside the legacy single `delimiter`; a level with only `delimiter` still serializes to `split(d,n)` byte-for-byte, so existing recipe hashes do not move. `naming: 'prefix'` is now meaningful on fixed levels, not only the variadic tail.

**Backward compatibility**: purely additive (SchemaVer ADDITION). Recipes without these filters validate, render, and hash unchanged. Spec URI did NOT bump.

### §4.13 `target.crosswalks[]`: a crosswalk column role (added 2026-09-21, SchemaVer 1.12.0; additive)

Crosswalker turns more of what is latent in a source into vault structure, and the import wizard is where the user decides, column by column, what becomes real. A [**crosswalk column role**](/crosswalker/concepts/terminology/#crosswalk-column-role) (plain: a source column whose cells contain identifiers from another framework) [reifies](/crosswalker/concepts/terminology/#reification) those references as first-class crosswalk-edge notes instead of leaving them as text or treating them as links inside the source ontology.

Each `target.crosswalks[]` entry has seven fields (source: `spec/recipe.schema.json § $defs/crosswalk_entry`):

| Field | Contract |
|---|---|
| `column` | Required non-empty source-column name. |
| `to_ontology` | Required non-empty CURIE prefix for the target ontology, for example `nist-csf-2`. |
| `predicate` | One of five allowed values: `is_equivalent_to`, `is_broader_than`, `is_narrower_than`, `is_approximate_to`, or `intersects_with`; default `is_approximate_to`. See [§6](#6-crosswalk-assertion-vocabulary-and-sssom-provenance) for their meanings. |
| `split` | Cell delimiters; default `[",", "\n", ";"]`. |
| `drop` | Atoms treated as empty; default `["None", "N/A", "-"]`. |
| `qualifier` | Either `keep-as-justification` or `strip`; default `keep-as-justification`. |
| `mapping_set_id` | Optional mapping-set identity; default `<source ontology>-to-<to_ontology>-<recipe id>`. |

For each declared entry, the engine derives edge rows and writes Tier 1 `crosswalk_edge_frontmatter` notes under `_crosswalker/mappings/<source>-to-<target>` (source: `src/generation/crosswalk-edge-pass.ts`). The notes have their own newly minted import set under the `sssom` identity prefix. Nothing is written into the concept note. The edge pass uses the same SSSOM identity and generation path as a standalone mapping import, then invokes Tier 2 projection and closure precomputation when those handles are available.

This is separate from `target.graph_edges` because the two keys describe different output shapes. `graph_edges` encodes intra-ontology relations as frontmatter on the concept note; a crosswalk column emits separate mapping notes. The SchemaVer 1.12.0 amendment makes the distinction explicit in `graph_edge.via`: `crosswalksTo (intra-vault convenience only; cross-ontology references belong in target.crosswalks)` (source: `spec/recipe.schema.json § $defs/graph_edge.properties.via`).

A trailing parenthetical qualifier is kept verbatim as `mapping_justification` when `qualifier` is `keep-as-justification`, and is removed when the value is `strip`. Crosswalker does not parse the qualifier for meaning in this contract (source: `deriveCrosswalkEdgeRows()` in `src/generation/crosswalk-edge-pass.ts`).

**CRI worked example.** The `NIST CSF v2 Mapping` column contains CSF identifiers that are byte-identical to CRI's own Profile identifiers. A wikilink would therefore resolve to a CRI note and manufacture a false intra-ontology relation. `recipes/import/cri-profile-v2-2.json` now declares the column as a crosswalk to `nist-csf-2`, uses `is_approximate_to`, and keeps qualifiers such as `(CRI Modified)` as justification. Its effective recipe hash moved because the recipe now produces additional edge notes; that output-changing declaration correctly participates in the hash.

The wizard offers this role through detection kind `crosswalk-column` in `src/import/detection.ts`, then shows a **Crosswalks** card where the user names the framework and chooses the predicate. The framework control lists registry ontologies plus **Other**, and the predicate control exposes the five schema values above (source: `src/import/workbench.ts`). An unnamed target blocks Generate with: `Column "<column>" is marked as a crosswalk but no framework is named. Pick the framework on the Crosswalks card, or turn the card off.` (source: `src/import/recipe-document.ts`).

`target.crosswalks` participates in `computeRecipeHash()` through `recipeHashCanonicalInput()` because it changes which notes exist. An absent key stays absent rather than becoming `null`, so every recipe without `target.crosswalks` keeps its pre-1.12.0 canonical input and hash byte for byte (source: `src/generation/hash.ts`).

**Backward compatibility**: purely additive (SchemaVer ADDITION). Recipes without `target.crosswalks` validate, generate, and hash unchanged. Spec URI did NOT bump.

<span id="source-nest"></span>
### §4.15 `source.nest[]`: nested record levels (added 2026-09-21, SchemaVer 1.13.0; additive)

Deeper [**reification**](/crosswalker/concepts/terminology/#reification) (plain: making implied source structure into first-class vault objects), and a good user experience for controlling that reification during import, now meet at source depth: a source whose records own lists of sub-records now imports as nested notes, and the wizard is where you decide which levels become notes and how each is named. The gap was a record that owned lists of sub-records but could previously become only one flat collection of rows.

Each `source.nest[]` entry has seven fields (source: `spec/recipe.schema.json § $defs/nest_level`):

| Field | Contract |
|---|---|
| `level` | Required non-empty level name. It must appear in `source.levels` and be used by `target.layout`. |
| `id` | Required template for this level's stable identifier, evaluated against the record. |
| `children` | On a JSON-backed level, the field name containing the next level's array; on a workbook or sibling-array level, a `$defs/source_join_from` locator for the secondary collection. The last level has no `children`. |
| `parent_key` | For join-sourced children, the child field that names its parent's id. It is required on the child level for that shape and ignored for JSON-field children. |
| `carry` | Optional unique field names copied into child lineage at `_cw.ancestors.<level>.<field>`. The id field is carried by default. |
| `leaf` | On a non-leaf level, `folder-note` writes that level's row at `<folder>/<folder>.md`, while `none` produces folders only and no note for that row. Every non-leaf level needs one of these values unless `target.layout` has a `file` entry for that level. The last level may declare `none` (its rows are not emitted, which is how the wizard's Depth select leaves deeper levels out of an import); `folder-note` on the last level is refused with `The last nest level "<level>" is the note itself; folder-note applies only to levels that have children.` (source: `src/import/recipe-document.ts`). |
| `identity` | `global` uses this level's id as the CURIE local part; `path` uses the escaped lineage path when ids repeat under different parents. The default is `global`. |

The schema states the producer contract verbatim (source: `spec/recipe.schema.json § source.properties.nest.description`):

```text
(1) emission is depth-first in document order, parent row before its children, then the next parent;
(2) every emitted row carries one reserved key `_cw`, an object with `level` (this level's name), `path` (array of ancestor ids root first, including self), `parent` (the immediate parent's id, or '' at level 0), and `ancestors.<level>.<field>` (the carried fields of each ancestor);
(3) identity 'path' joins escaped pieces with '/';
(4) leaf 'folder-note' lands at <folder>/<folder>.md;
(5) source.where is evaluated per emitted row after `_cw` is attached and does not cascade from parent to child.
```

Under the [schema-as-primitive commitment](/crosswalker/concepts/etl-and-import/), an external Tier 1 producer must reproduce those five rules to emit the same nested notes and hash-match the plugin. A producer that chooses different rules is expressing a different recipe, not an invalid producer.

**Placement.** `render()` applies only layout entries at or above the emitted row's declared level. A non-leaf row without its own `file` entry uses its declared `leaf`: `folder-note` derives a file from the final folder segment, and `none` emits no note for that row (source: `src/render/index.ts`). Rows without `_cw` still apply the full layout exactly as before.

**Identity.** Identity is declared per level, pinned when the import set is minted, and never inferred from the current run. A plain `/` is not a safe boundary because `/` is already legal inside the CURIE local-part charset, so `['a/b', 'c']` and `['a', 'b/c']` would otherwise collide. `pathIdentityLocalPart()` first escapes every declared id and the reserved token marker, replaces a slash inside a piece with `--2f--`, then joins the escaped pieces with `/` (source: `src/generation/curie.ts § pathIdentityLocalPart`). Before the first folder is created, the engine computes every emitted CURIE and refuses the first duplicate with the exact message:

```text
Ambiguous identity <curie> claimed by rows at <path A> and <path B>. Set identity: path on level "<level>" so each row is named by its place in the hierarchy.
```

Source: `src/generation/generation-engine.ts § nestedIdentityCollision`.

**Join-sourced children.** A workbook sheet or sibling JSON array uses the same `source_join_from` locator and `resolveSecondaryRows()` path as `source.joins`; the secondary collection is read once per level and grouped by the child level's `parent_key` through the same normalized key rule (source: `src/source/nest.ts`, `src/source/joins.ts`). Rows naming no present parent are counted and warned once as `<n> <level> records name a parent that is not in the source and were not imported.` A CSV is one collection, so join-sourced nesting is refused rather than pretending a second collection exists.

**OSCAL-mini worked example.** This three-level shape makes the required non-leaf leaves explicit while keeping the §3.2 source and layout pattern:

```json
{
  "source": {
    "ontology": "oscal-mini",
    "levels": ["group", "control", "part"],
    "nest": [
      { "level": "group", "id": "{id}", "children": "controls", "carry": ["title"], "leaf": "folder-note" },
      { "level": "control", "id": "{id}", "children": "parts", "carry": ["title"], "leaf": "folder-note" },
      { "level": "part", "id": "{id}" }
    ]
  },
  "target": {
    "layout": [
      { "level": "group", "mechanism": "folder", "template": "{_cw.ancestors.group.id|fs-safe}" },
      { "level": "control", "mechanism": "folder", "template": "{_cw.ancestors.control.id|fs-safe}" },
      { "level": "part", "mechanism": "file", "template": "{id|fs-safe}.md" }
    ]
  }
}
```

For group `ac`, control `ac-1`, and part `ac-1_smt`, the three row addresses are `ac/ac.md`, `ac/ac-1/ac-1.md`, and `ac/ac-1/ac-1_smt.md` (source: `src/render/index.ts`, `tests/render-nest.test.ts`).

**Wizard control surface.** Detection kind `nested-records` recognizes eager JSON record arrays recursively to four levels when at least 80% of sampled parent rows share an object-array field (source: `src/import/detection.ts`). The JSON picker reports the observed chain once, on the top-level candidate, then offers `Nested: <levels> (<n> notes)` and `Only <list> (<n> notes)`; the flat choice remains selected until the user chooses nesting (source: `src/import/import-wizard.ts`). The mapping card leads with a **Depth** select that sets `leaf: folder-note` on every level above the note and `leaf: none` on every level below it (source: `setFolderDepth` in `src/import/mapping/view-model.ts`). Nested workbench rows expose **Own note** with **Yes, as a folder note** or **No, folder only**, and **Identified by** with **Its own identifier** or **Its path from the top level**. Merge and Split are not offered on nested rows because the source already declares the record-type boundaries, and merging two record types into one name would create a collision rather than project children into a parent's body (source: `src/import/workbench.ts`).

**Hash and source namespace.** `source.nest` participates in `computeRecipeHash()` because it changes which notes exist. Absence stays absent instead of becoming `null`, so every recipe without `nest` keeps its previous canonical input and hash byte for byte (source: `src/generation/hash.ts § recipeHashCanonicalInput`). A source column literally named `_cw` is refused with `Column "_cw" is reserved for nested-record lineage. Rename it in the source and import again.` because `_cw` belongs to the producer contract (source: `src/source/joins.ts § assertNoReservedSourceColumn`).

**Limits.** JSON-field nesting requires an eager source; a streamed source with `nest` is refused with an action to import without streaming (source: `src/source/index.ts`). A join-backed nested import previews the primary row count until generation reads the secondary collection and computes the exact emitted count. Wizard detection stops at four levels, so deeper nesting is outside this build's stated scope. Recursive shapes are walked only to the depth explicitly declared in `source.nest` (source: `src/import/detection.ts`, `src/source/nest.ts`). The deferred capability remains plain: parts as sections under their control is not a layout shape and is not in this build.

**Backward compatibility**: purely additive (SchemaVer ADDITION). Recipes without `source.nest` validate, generate, and hash unchanged. Spec URI did NOT bump.

### TypeScript shape

```typescript
interface JunctionNote {
  // === The 13 stored fields ===

  // Mandatory (5)
  link_type: 'evidence_link';          // discriminator; future link types may exist
  evidence: string;                    // wikilink: '[[Evidence/MFA-Policy]]'
  control: string;                     // wikilink: '[[Frameworks/NIST-800-53-r5/AC-2]]'
  ontology: string;                  // 'nist-800-53-r5' (denormalized for Bases query)
  status: 'implemented' | 'partial' | 'planned' | 'alternative' | 'not-applicable';

  // Optional (8)
  confidence?: number;                 // 0.0 - 1.0
  evidence_type?: 'policy-document' | 'automated-scan' | 'test-result'
                | 'configuration' | 'log-export' | 'interview'
                | 'architecture-review' | 'attestation';
  method?: string;                     // free-text or controlled vocab: 'manual-review', 'config-scan'
  reviewer?: string;                   // wikilink to person note: '[[People/Alice]]'
  review_date?: string;                // ISO 8601
  responsible?: string;                // wikilink: '[[People/Bob]]' (responsible party)
  collected?: string;                  // ISO 8601 (when evidence was collected)
  expires?: string;                    // ISO 8601 (when evidence becomes stale)

  // === Computed at query time (not stored) ===
  freshness?: 'fresh' | 'stale' | 'expired' | 'not-set';

  // === Optional (for review chains) ===
  supersedes?: string;                 // wikilink to previous junction note

  // === Standard Crosswalker fields ===
  _crosswalker?: CrosswalkerMetadata;  // junction notes also carry this
}
```

### Filename convention

`Junctions/{ontology}/{control_id}--{evidence_slug}.md` — e.g., `Junctions/nist-800-53-r5/AC-2--MFA-Policy.md`.

The composite filename (control + evidence) makes diff-on-rename easy and prevents collision when one piece of evidence implements multiple controls.

### Mandatory vs optional fields (rule)

- **Mandatory (5)**: `link_type`, `evidence`, `control`, `ontology`, `status`. Plugin generation refuses to create a junction note missing any of these. Bases queries assume their presence.
- **Optional (8)**: `confidence`, `evidence_type`, `method`, `reviewer`, `review_date`, `responsible`, `collected`, `expires`. Pluginrenders missing as `null`/empty.
- **Computed**: `freshness` derived from `review_date` + `expires` at query time (Tier 1: in-memory; Tier 2: SQL view).

### OSCAL `by-component` mapping

The 13-field schema is structurally isomorphic to OSCAL's `by-component` assembly per [Ch 07 deliverable](/crosswalker/agent-context/zz-log/2026-04-10-evidence-link-edge-model-synthesis/). The OSCAL export pipeline is straightforward field-rename. See [`reference/registry/oscal`](/crosswalker/reference/registry/oscal/) for the mapping table once the OSCAL mental-model doc lands.

## §6 Crosswalk assertion vocabulary and SSSOM provenance

A crosswalk assertion (one stated relationship between two concepts) stores its relationship in `predicate_id` and any explicit negation separately in `predicate_modifier`. The 8 allowed predicates are sourced from `spec/tier1.schema.json § $defs.crosswalk_edge_frontmatter.properties.predicate_id`:

| `predicate_id` | Plain meaning | Group |
|---|---|---|
| `is_equivalent_to` | The concepts have the same meaning for the mapping purpose | Set-theoretic |
| `is_broader_than` | The subject covers more than the object | Set-theoretic |
| `is_narrower_than` | The subject covers less than the object | Set-theoretic |
| `is_approximate_to` | The concepts are similar but not equivalent | Set-theoretic (Crosswalker extension) |
| `intersects_with` | The concepts overlap | Set-theoretic |
| `no_relationship` | The source explicitly asserts no relationship | Set-theoretic |
| `superseded_by` | The subject was replaced by the object in a later release | Release lineage |
| `supersedes` | The subject replaces the object, which is from an earlier release | Release lineage |

`predicate_modifier` is absent for a positive assertion or exactly `NOT` for explicit negation. Negation is not encoded by inventing an `_NOT` predicate name. A negative equivalence therefore remains `predicate_id: is_equivalent_to` plus `predicate_modifier: NOT`.

**Release lineage is an ordinary crosswalk, not a subsystem** (added 2026-08-28, Ch 43). A version transition is a mapping between two release ontologies: a rename is one edge, a split is N edges sharing `subject_id`, a merge is N edges sharing `object_id`. Both directions are named because the effective-edge traversal in `src/tier2/queries.ts` materialises each stored assertion's inverse into query rows, so the inverse spelling has to be a value that exists. Both are transitive: a successor walk has to cross several releases (source: `src/tier2/predicate-characteristics.ts`).

The lineage pair is deliberately **not** set-theoretic, and the two set-theoretic exporters refuse rather than translate it. `superseded_by` has no OLIR relationship type and no SKOS mapping property, so a lineage edge is excluded from both the STRM/OLIR TSV and the SSSOM TSV export and reported as `lineage-predicate-not-representable-in-strm` (source: `src/export/strm-tsv-exporter.ts`, `src/export/sssom-exporter.ts`). Coercing it would have published a withdrawal record as the claim that two controls intersect.

SSSOM (the Simple Standard for Sharing Ontological Mappings) provenance is carried by `mapping_set_id`, `match_type`, `match_confidence`, `mapping_justification`, `mapping_provider`, `mapping_date`, `creator_id`, and `review_status`. Direct SSSOM-style queries and export preserve mapping-set provenance and negation. STRM export omits negated assertions because STRM cannot represent that modifier without changing meaning.

## §7 Tier 2 sidecar SQL schema (sqlite-wasm projection)

The Tier 2 sidecar is a **deletable, recoverable projection** of Tier 1 frontmatter into SQLite tables. It exists to enable performant queries (transitive closure, multi-ontology joins, coverage matrices, perspective views) that are awkward over markdown frontmatter.

**Recovery property** (load-bearing): if `.crosswalker.sqlite` is missing, corrupted, or stale, the projector rebuilds it from canonical Tier 1 on next vault load. This is what makes Tier 2 risk-free to bundle in v0.1.

:::tip[Substrate choice — verified 2026-08-21]
v0.1 ships `@sqlite.org/sqlite-wasm` as the embedded query substrate. `sqlite-vec` remains a decoupled optional vector layer and is deferred; the next calendar-anchored packaging revisit is 2026-11-06. See the [Tier 2 substrate synthesis](/crosswalker/agent-context/zz-log/2026-05-04-tier-2-substrate-synthesis/) and [WASM-A pivot synthesis](/crosswalker/agent-context/zz-log/2026-05-06-wasm-a-pivot-synthesis/).
:::

### Current schema summary

`src/tier2/schema.sql` is the canonical DDL. Tier 2 currently ships as `tier2-sqlite-v6`. The table below cites every stored column by table so additions are reviewable without copying a second SQL source that can drift.

| Table/view | Current columns | Purpose |
|---|---|---|
| `schema_meta` | `key`, `value` | Schema and projection metadata |
| `ontologies` | `id`, `name`, `version`, `base_path`, `upstream_url`, `recipe_id`, `imported_at`, `control_count` | One represented ontology summary |
| `concepts` | `ontology_id`, `curie`, `vault_path`, `source_hash`, `import_set_id`, `title`, `review_cid`, `review_wording_cid`, `review_scope_cid`, `review_housekeeping_cid`, `parent_curie`, `status`, `imported_at`, `modified_at` | Canonical concept projection with explicit parent identity and current review fingerprints |
| `mappings` | `import_set_id`, `mapping_set_id`, `subject_id`, `predicate_id`, `predicate_modifier`, `object_id`, `match_type`, `match_confidence`, `mapping_justification`, `mapping_provider`, `mapping_date`, `creator_id`, `review_status`, `source_path`, `source_hash` | One mapping occurrence with release provenance and explicit negation |
| `junction_notes` | `vault_path`, `curie`, `subject`, `subject_curie`, `predicate`, `object`, `object_curie`, `coverage`, `reviewer`, `review_date`, `status`, `confidence`, `scope`, `expires_at`, `notes`, `reviewed_against_curie`, `reviewed_against_cid`, `reviewed_wording_cid`, `reviewed_scope_cid`, `reviewed_housekeeping_cid`, `import_set_id`, `source_hash`, `modified_at` | Evidence relationship with separate addresses and identities. The subject/whole-row pair projects together; group hashes project only as one complete three-value block (source: `src/tier2/projector.ts § upsertJunctionNote`) |
| `junction_notes_with_freshness` | All junction columns plus computed `freshness`, `subject_baseline`, and `change_kind` | Review-age and content-drift view. `review_cid` alone gates `subject_baseline = changed`; only then does `change_kind` compare the three group hashes in priority order `wording` > `scope` > `housekeeping`. A changed legacy baseline without complete group hashes defaults conservatively to `wording`, so it cannot enter the housekeeping dismissal path (source: `src/tier2/schema.sql § junction_notes_with_freshness`) |
| `closure_cache` | `subject_id`, `predicate_id`, `object_id`, `shortest_depth`, `computed_at` | Cached transitive answers |
| `closure_cache_state` | `subject_id`, `predicate_id`, `computed_max_depth`, `computed_at` | Proof that a closure partition was computed through a depth, including empty results |
| `concept_embeddings` | Reserved virtual-table shape | Optional future vector projection; not authoritative |

The mapping primary key includes `mapping_set_id`, the subject/predicate/modifier/object assertion, and `source_path`. Separate releases and duplicate source occurrences therefore do not overwrite one another. Endpoint indexes cover mapping subjects/objects and junction `subject_curie`/`object_curie`.

### Projection rules (Tier 1 → Tier 2)

1. Read only notes with valid `_crosswalker` provenance; canonical Markdown remains the authority.
2. Project `_crosswalker.import_set.id` to nullable `import_set_id` on concepts, mappings, and junction notes. Legacy unstamped records project `NULL`.
3. Project concept `parent_curie` directly. Never derive it from the `parent` wikilink.
4. Project junction `subject_curie` and `object_curie` directly. Never derive them from wikilink text.
5. Normalize mapping-set identifiers and predicate modifiers through the shared provenance helpers, then store each mapping occurrence with its source path.
6. Reconcile an ontology's displayed version deterministically across projected concepts using binary lexical order, so file traversal order cannot change the result.
7. Exclude `predicate_modifier = 'NOT'` from effective graph edges, including symmetric and inverse expansion. Direct `crosswalkBetween()` queries retain negated rows and their provenance.
8. Invalidate mapping-dependent closure rows and depth-coverage state together whenever mappings change.
9. Prune unseen rows only during a complete `full` projection. Filters, projection errors, or unreadable-but-present frontmatter suppress pruning.
10. Project `review_groups` only when all three schema-defined hashes are present. Compare them only after the whole-row `review_cid` differs; apply `wording` > `scope` > `housekeeping` so one attestation receives exactly one change kind.

### Schema-version migration

Tier 2 now ships `tier2-sqlite-v6`. Because Tier 2 is derived, opening any other schema version drops and recreates the sidecar, then reprojects canonical Tier 1 Markdown. v6 adds current and recorded wording/scope/housekeeping hashes and the computed `change_kind`; v5 introduced the whole-row `review_cid` gate and baseline pair. It preserves the v4 ownership projection and the v3 mapping-occurrence, negation, endpoint-identity, and depth-safe closure-cache model.

## §8 Cross-schema invariants & constraints

These are the rules the projector and import paths both respect:

1. **Contracts stay distinct:** the Recipe Schema Contract governs ImportRecipe intent; the Tier 1 Schema Contract governs canonical member records.
2. **Tier 1 is canonical local managed authority:** every Tier 2 column has a Tier 1 source. No authoritative managed knowledge lives only in Tier 2.
3. **Knowledge Set is conceptual, not a universal envelope:** ontology, mapping-set, and evidence-set aggregates may be represented through Tier 1 members without one generalized aggregate schema.
4. **Managed ownership is declared:** a producer may update or clear only recipe-declared managed fields and `_crosswalker` provenance. `user_preserve` fields remain untouched.
5. **Identity is not address:** `parent_curie`, `subject_curie`, and `object_curie` are explicit stable identities; wikilinks remain clickable addresses and are never reverse-parsed into identity.
6. **Mandatory junction fields:** `curie`, `subject`, `predicate`, `object`, and `_crosswalker` (source: `spec/tier1.schema.json § $defs.junction_note_frontmatter.required`).
7. **Crosswalk vocabulary and negation are separate:** `predicate_id` has 8 allowed relationship values, while `predicate_modifier` is absent or `NOT` (source: `spec/tier1.schema.json § $defs.crosswalk_edge_frontmatter.properties`).
8. **Mapping occurrences preserve release provenance:** `mapping_set_id` distinguishes published mapping collections; deterministic assertion CURIEs distinguish repeated occurrences without changing concept identity.
9. **Graph traversal uses only positive assertions:** direct queries may return negated assertions, but closure, symmetric expansion, and inverse expansion exclude `NOT`.
10. **Version-governed representations rebuild safely:** ImportRecipe, Tier 1 records, and Tier 2 SQL carry independent versions appropriate to their roles. Tier 2 can be discarded and regenerated.

## §9 Build sequence

The original v0.1 implementation plan decomposed the governing contracts and representations in this order:

1. **`_crosswalker` metadata v2** — extend existing `src/generation/generation-engine.ts` to write the v2 fields. Lowest-risk: this is just a frontmatter shape change.
2. **Junction note 13-field schema** — implement junction-note generation as a new code path in the generation engine. Triggered by ImportRecipe with crosswalks that target evidence documents.
3. **ImportRecipe v2** — refactor `src/types/config.ts` to the v2 shape. Migration script for existing v1 saved configs.
4. **Tier 2 sidecar SQL projector** — new module in `packages/core/`. Auto-runs on vault load. Lazy closure cache + sqlite-vec embedding integration.

Each step has a corresponding test:
- Round-trip test: write Tier 1 frontmatter, project to Tier 2 SQL, query, confirm semantic equivalence to source data.
- Idempotency test: project twice; second projection is a no-op.
- Recovery test: delete the .sqlite, reload, confirm reprojection produces byte-identical state.
