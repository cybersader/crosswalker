Before-state lives on the attestation, not in Tier 2 history. :::caution[Two different "version" problems — do not conflate them]
Crosswalker already has a migration policy for **its own** `_crosswalker` frontmatter schema (`crosswalker-v1` → `crosswalker-v2`, see [the schema-version migration policy](/crosswalker/agent-context/v0-1-schema-spec/#schema-version-migration)) — additive transforms, `previous_ids` aliasing, idempotent, resumable. **That is not this challenge.** This challenge is about the **source ontology** changing — NIST publishes CSF 2.0, MITRE bumps ATT&CK, CIS ships Controls v8 — while concepts already live in a user's vault with evidence links, `user_preserve` fields, and crosswalk edges hanging off them. Keep the two axes distinct throughout the brief; conflating them is the single most likely way to produce a useless deliverable.
:::

## Why this exists

Surfaced 2026-07-11 in a local architect working draft (`.workspace/2026-07-11-thinking-big-the-lifecycle-arc.md`, gitignored per the [research-artifact lifecycle](/crosswalker/agent-context/zz-research/) convention — pre-decision drafts stay local; see the [workbench synthesis log](/crosswalker/agent-context/zz-log/2026-07-11-shape-workbench-architecture-synthesis/) for the public record of the build era it closes). The owner's reframe: Crosswalker is not an importer, it's **the place ontologies live** — a five-act product where **Act 1 (import)** is what v0.1.6 ships, and **Act 2 (live with it)** — "framework versions update; Crosswalker shows a semantic diff vs your vault and runs a guided migration preserving user notes, links, evidence" — is the proposed **headline of v0.2**, not a footnote. The strategic bet: "import anything" is a feature list; "your frameworks update and your world survives" is a moat.

The Act 2 sketch (match pass → impact pass → review UI → apply → audit) is architect-drafted, not stress-tested. This challenge is that stress test — specifically against how publishers **actually** behave, not how a tidy diff algorithm would like them to behave.

## What to investigate

1. **Match-pass feasibility against real publisher behavior.** For each of NIST (CPRT-published CSF/800-53), MITRE ATT&CK (STIX 2.1), and CIS Controls: are curies stable enough for **curie-exact match** to carry most of the load, or do publishers routinely rename the identifier itself (CSF's `PR.AC-1`→`PR.AC-01` says no)? Which publishers ship a **machine-readable rename/crosswalk table** (MITRE's STIX `x_mitre_deprecated`/`revoked` fields + CTID mappings; NIST CPRT's own crosswalk artifacts) vs which don't (CIS v7→v8 — Excel or PDF only, per [framework-versioning](/crosswalker/concepts/framework-versioning/))? Where no table exists, what's the honest ceiling for SSSOM-style lexical/structural fallback matching (label similarity, hierarchy-position similarity) run in-plugin, TS-only, on mobile — not an OAEI-grade ML matcher?
2. **The two axes of change.** Distinguish **source-version change** (the framework itself changed between v-old and v-new) from **recipe change** (the same source data, but the user edited how it renders — a workbench mapping edit, a new preset). Does `render()`'s [determinism/Pass-1 hashability](/crosswalker/agent-context/zz-log/2026-05-04-target-structure-synthesis/) give this apart for free — unchanged content hash + changed recipe hash = pure recipe change, no semantic diff needed — or does the system need an explicit signal? What happens when **both** change at once (re-import v-new with an also-edited recipe)?
3. **Split/merge semantics for evidence reassignment.** When a curie splits (ATT&CK's `T1086`→`T1059.001`, nested under a new parent) or merges (CIS's control consolidation, 20→18), what happens to the artifacts hanging off the old concept — evidence junction notes, `user_preserve` frontmatter, crosswalk edges pointing at it? Is `previous_ids: string[]` (already shipped, one-to-many *toward* the old side) sufficient, or does split/merge need a richer many-to-many lineage shape? Does a "moved concept drags its evidence links along" default make sense, or does split specifically require a forced human choice (which of the N new concepts does the old evidence now belong to)?
4. **Lineage storage.** Where does "this note descends from v-old's `AC-2`" actually live — an extended `previous_ids`-style frontmatter field (cheap, but not natively graph-queryable), a sidecar mapping file shaped like an SSSOM mapping set (queryable via the same Tier 2 machinery already built for crosswalks), or `graph_edges` (schema-reserved, per [Ch 22](/crosswalker/agent-context/zz-challenges/archive/22-target-structure-expressivity/))? Whichever wins, does it compose with [the Bases query layer](/crosswalker/reference/roadmap/milestones/v0-1-6-bases-query-layer/) and the [audit-trail](/crosswalker/reference/roadmap/milestones/v0-1-8-audit-trail/) git substrate, or fight both?
5. **Confidence thresholds + human-in-the-loop UX.** The lifecycle-arc sketch proposes reusing "the workbench pattern again" — change-set list + impact preview + per-change accept/redirect. At Act 1 scale that's dozens of column-mapping decisions; at Act 2 scale a framework update can touch hundreds or thousands of concepts. What's the actual UX when 95% of changes are high-confidence curie-exact matches that shouldn't need a click, and 5% are ambiguous splits/merges that must? Where's the line between "auto-apply" and "block on review," and who sets it?
6. **Determinism + replayability.** Should a migration be replayable/hashable the same way `render()` is — i.e. does the [golden-vault testing doctrine](/crosswalker/agent-context/zz-log/2026-07-11-shape-workbench-architecture-synthesis/) extend to "re-running this migration on the same two source versions produces a byte-identical change-set and a byte-identical vault"? What has to be true of the match pass for that to hold (deterministic tie-breaking on ambiguous matches, not "pick whichever the fuzzy matcher liked best today")?
7. **Is "a version bump IS a crosswalk" actually true?** The lifecycle-arc sketch frames match-pass output as reusable SSSOM machinery (v-old→v-new mapping set, same `mapping_justification`/`confidence` envelope as a cross-framework crosswalk). Stress-test this: does a same-ontology version-to-version mapping actually behave like a cross-ontology crosswalk (symmetric, framework-agnostic predicates), or does it need version-specific semantics (e.g., a `supersedes`/`superseded_by` predicate that STRM's 5-relationship vocabulary doesn't currently name) that would extend, not reuse, the committed [STRM](/crosswalker/reference/registry/strm/) + [SSSOM](/crosswalker/reference/registry/sssom/) stack?
8. **Worked examples over real corpora.** At minimum: NIST CSF 1.1→2.0 (id rename + new function added — what does the match pass resolve automatically vs flag?), MITRE ATT&CK's July 2020 sub-technique migration (`T1086`→`T1059.001` — a split-and-nest, machine-readable via STIX), and CIS Controls v7→v8 (renumbered/consolidated, **no** machine-readable diff — what's the fallback when publisher tooling gives you nothing?). For each: what fraction of concepts match cleanly, what fraction need the fallback matcher, what fraction need a human, and does the corpus already exist in this repo (`test-vault/Crosswalker Test Data/`, the framework corpus) to actually run this rather than reason about it abstractly?

## Deliverable shape

- A recommended match-pass design (curie-exact primary + explicit fallback tier[s]) **or** a defensible argument that fallback matching is out of scope for v0.2 and curie-exact + human-review-on-miss is sufficient — with evidence from the worked examples, not assertion.
- An explicit split/merge evidence-reassignment contract, including whether `previous_ids` needs a schema extension.
- A verdict on the source-version-vs-recipe-change distinction: is it free from existing determinism machinery, or does it need a new signal?
- A lineage-storage recommendation (frontmatter extension vs sidecar vs graph edges) that names its Bases-queryability and audit-trail implications.
- A verdict on whether match-pass output should extend the SSSOM/STRM stack or needs version-specific predicate semantics.
- At least two real-corpus worked examples with concrete match/fallback/human-review percentages, not hypothetical framework descriptions.
- A "wire now (v0.2) vs defer" call on each open question, given the owner's proposed reframe that Act 2 is v0.2's headline, not a stretch goal.

## Anti-patterns

- **Assuming publishers provide clean machine-readable rename tables.** Only MITRE (STIX) reliably does; NIST is partial (CPRT crosswalk artifacts, mostly Excel-shaped); CIS provides essentially nothing machine-readable. Design for the CIS case, not the MITRE case, or the design is fiction.
- **Building an OAEI-grade ML/embedding-based ontology matcher for v0.2.** Breaks [commitment #3](/crosswalker/concepts/etl-and-import/) (mobile-Obsidian portability, TS in-plugin, small-OSS-contributor pool). SSSOM-style lexical/structural matching with explicit, auditable rules is the ceiling; justify anything beyond it.
- **Conflating internal `_crosswalker` schema-version migration with source-ontology version migration** — see the caution callout at the top. They share vocabulary ("migration," "version") but are different problems with different solved-vs-open status.
- **Silent auto-apply of low-confidence matches.** The whole point of Act 2 is that the user's work survives *honestly reviewed*, not silently reshuffled — echoes the [connectedness mandate](/crosswalker/agent-context/zz-log/2026-07-11-shape-workbench-architecture-synthesis/)'s core lesson from Act 1 (silent behavior is the failure mode, not a baseline to preserve).
- **Treating "semantic diff" as one monolithic operation.** The sketch already decomposes it into match / impact / review / apply phases — don't flatten that back down; each phase has different failure modes and different automatability ceilings.
- **Ignoring that this is a mid-vision-not-yet-built area.** [Ontology evolution](/crosswalker/concepts/ontology-evolution/) and [data model resilience](/crosswalker/agent-context/data-model-resilience/) already did real thinking here in the Foundation phase (2026-04) — pre-`render()`, pre-recipe, pre-workbench. Read them before re-deriving SCD Type 2/3 or bitemporal tracking from scratch; the job is to check that vision against what actually shipped, not to ignore it.

## Success criteria

- A concrete, evidence-backed match-pass design (or defensible "curie-exact + human-review is enough for v0.2" verdict) tested against at least the CSF, ATT&CK, and CIS worked examples.
- Explicit split/merge evidence-reassignment semantics, with a stated verdict on whether `previous_ids` needs a schema change.
- A clear answer to whether source-version-change and recipe-change are already distinguishable via existing determinism/hashing machinery.
- A lineage-storage recommendation compatible with `managed`/`user_preserve`, Bases, and the audit trail.
- An explicit "wire now vs defer to v0.3+" call per open question, given the proposed v0.2-headline framing.
