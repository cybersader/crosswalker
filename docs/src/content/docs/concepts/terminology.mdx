## Artifact roles and authority

Crosswalker separates **what an artifact means** from **where or how it is stored**. Owning page: [artifact roles and authority](/crosswalker/concepts/artifact-roles-and-authority/).

| Term | Plain English | Definition |
|---|---|---|
| <span id="schema-contract"></span>**Schema Contract** | *the rules for what counts as valid* | Plainly: the machine-checked **rulebook** that spells out which properties a valid note or recipe may carry — the plugin, an outside script, and an agent all validate against the same rulebook before writing, which is what makes external producers first-class. Formally: a normative, versioned representation contract answering "what is valid?" The JSON Schema files in `spec/` carry these. A Schema Contract governs artifacts; it is not content itself. |
| <span id="knowledge-set"></span>**Knowledge Set** | *the actual content — what exists* | A named, versioned, governed collection of concepts or assertions. A conceptual superclass, not a claimed generalized `KnowledgeSet` file format. |
| <span id="recipe"></span>**Recipe** | *the instructions — what should be done* | A portable, schema-validated declaration of repeatable behavior. [`ImportRecipe`](#import-recipe) is the concrete source-to-Tier-1 subtype. A Recipe is not a Knowledge Set, a run receipt, generated output, or a package. |
| <span id="import-set"></span>**Import set** | *the collection of notes one import owns* | A durable ownership boundary with a meaningless id minted at first import and stamped into every note that run produces. Refreshes select and reuse the set; ownership is never derived from recipe, source, destination, or note identity. [Decision and rationale](/crosswalker/agent-context/zz-log/2026-08-21-import-set-ownership/) |
| <span id="execution-record"></span>**Execution Record** | *the receipt — what actually happened* | A future historical record of one run: verified inputs, exact recipe identity, outcomes, validation, warnings, output inventory. Today's per-note provenance is not yet a complete Execution Record. |
| <span id="package-manifest"></span>**Package Manifest** | *the shipping label — what was distributed* | A future distribution and attestation envelope: resolved artifacts, dependencies, hashes, licenses, signatures, install rules. No normative contract is claimed yet. |
| <span id="tier-1-authority"></span>**Tier 1** | *the real copy, on disk* | Crosswalker's canonical managed Markdown representation of Knowledge Sets. A representation and authority tier, not a peer root artifact class. See [tiers](#tiers). |

### Recipe roles

Roles *around* the [Recipe](#recipe) family — not four new artifact classes.

| Role | Meaning |
|---|---|
| **Recipe specification** | The canonical machine-evaluable declaration, governed by a Recipe [Schema Contract](#schema-contract). |
| **Recipe template** | Parameterized or default policy to instantiate a specification from. A Shape Preset is one. |
| **Recipe binding** | A recipe reference plus concrete parameters, source identity, or other selected bindings. |
| **Recipe execution** | One run of a bound recipe. The Recipe states intent; a separate [Execution Record](#execution-record) reports the outcome. |

### Mapping disambiguation

| Term | Definition |
|---|---|
| <span id="mapping-set"></span>**MappingSet** | Plainly: **one published crosswalk release** — the whole collection of mapping assertions shipped together (e.g. NIST's 800-53 Rev 4 → Rev 5 mapping). Formally: a [Knowledge Set](#knowledge-set) subtype with its own identity, version, membership, provenance, license, and publication state. Not an [ImportRecipe](#import-recipe), and not a folder inferred from edge rows. |
| <span id="mapping-assertion"></span>**MappingAssertion** — *also:* assertion | Plainly: **one claimed fact about how two things relate** — a single crosswalk row, "AC-2 is equivalent to A.9.2.1." Someone asserted it, so it can be right, wrong, disputed, or superseded — which is why every assertion carries where it came from. Formally: one subject–predicate–object correspondence inside a MappingSet, optionally carrying confidence, justification, provenance, and review metadata. |
| <span id="import-mapping"></span>**ImportMapping** | An editable, source-bound workbench projection of how source fields map into Recipe-owned regions. Implementation state around an ImportRecipe — not a MappingSet or a portable artifact. |

### Representation and distribution terms

| Term | Definition |
|---|---|
| <span id="live-view"></span>**Live view** | A query-backed view recomputed from current data on read or refresh. [Bases](/crosswalker/concepts/metadata-ecosystem/) views are live views, not stored results. |
| <span id="materialized-snapshot"></span>**Materialized snapshot** | Query results computed once and persisted — reproducible, potentially stale. Useful for publishing, audit, and comparison; storing one does not make it canonical. |
| <span id="package"></span>**Package** | A semantically resolved release described by a [Package Manifest](#package-manifest): selected artifacts plus dependency, integrity, license, and install meaning. |
| <span id="carrier"></span>**Carrier** | The physical container that moves the bytes — a zip, directory, or git repo. A carrier is not a Package by itself. |
| <span id="projection"></span>**Projection** | Always use with a qualifier: *field* projection, *read/view* projection, *Tier 1 → Tier 2* projection, or *editable UI* projection. ImportRecipe generation is broader than projection — it decodes and re-embodies source structure. |

## Core terms

| Term | Definition |
|------|-----------|
| **Ontology** | A structured representation of knowledge — categories, relationships, rules. A governed one is a kind of [Knowledge Set](#knowledge-set). |
| <span id="reification"></span>**Reification** (plain: making implied structure into first-class things) | Turning structure that is only *latent* in a source, such as a hierarchy encoded in an ID column, a crosswalk encoded in a "maps to" column, or a category encoded in a tags column, into addressable vault objects: concept notes, junction notes (edges as notes), tags, and typed wikilinks. Crosswalker's core verb; the [ontology lifecycle](/crosswalker/concepts/ontology-lifecycle/) page states the product in these terms. Honest scope: hierarchy, tags, frontmatter, body, inbound cross-mapping columns, [nested record lists](#nested-record-level), and nested levels folded into their parent note as [sections](#section-record) now reify through the wizard; the `tag` and `wikilink` layout mechanisms remain deferred to v0.2. The [import wizard](/crosswalker/features/import-wizard/) is the control surface for reification: what becomes a folder, a tag, a link, an edge note, a nested note, or a section inside a note is decided there. |
| **Framework** | A specific ontology: NIST 800-53, CIS Controls, MITRE ATT&CK. |
| <span id="curie"></span>**CURIE** | A *compact URI* — `prefix:local`, e.g. `nist-800-53:AC-2`. Crosswalker's stable **concept identity**: the same CURIE means the same concept no matter where the note sits. [W3C CURIE Syntax 1.0](https://www.w3.org/TR/curie/) · [mapping into Obsidian](/crosswalker/concepts/mapping-into-obsidian/) |
| <span id="conceptidentity"></span>**ConceptIdentity** | A concept's CURIE plus its source attributes — the input to [`render()`](#render). Identity is fixed; vault layout is a recipe choice. |
| <span id="import-recipe"></span>**ImportRecipe** | A [Recipe](#recipe) subtype governing deterministic source-to-Tier-1 generation: the closed 5-mechanism grammar (`folder \| file \| heading \| tag \| wikilink`) × ordered `layout` × `also_emit` × enrichment × `graph_edges`. Distinct from a [SavedConfig](#data-flow-and-implementation-terms), a [MappingSet](#mapping-set), and the generated notes. [Recipe grammar](/crosswalker/agent-context/zz-log/2026-05-04-target-structure-synthesis/) · [fidelity boundary](/crosswalker/agent-context/zz-log/2026-07-21-portable-import-recipe-fidelity-synthesis/) |
| <span id="render"></span>**render()** | The pure function `render(Recipe, ConceptIdentity) → Address` — the single coupling point turning a concept + recipe into its path, heading anchor, wikilink target, tags, frontmatter, and body regions. Deterministic and reproducible. [System model](/crosswalker/concepts/system-model/#from-source-to-structure--render--the-5-mechanisms) |
| <span id="tiers"></span>**Tier 0 / 1 / 2** | Storage tiers, not peer artifact classes. **T0** = upstream source data · **T1** = the canonical Markdown in your vault (the real copy) · **T2** = a deletable SQLite cache derived from T1. [System architecture](/crosswalker/concepts/system-architecture/) |
| <span id="managed-user-preserve"></span>**managed / user_preserve** | The frontmatter ownership split: `managed` keys belong to the recipe (overwritten on re-import); `user_preserve` keys are yours (never overwritten). [Rationale](/crosswalker/agent-context/zz-log/2026-05-04-target-structure-synthesis/) |
| <span id="data-morphology"></span>**Data morphology** | The output-layer language: data *shape* plus three knobs — transform · reshape · draw — for describing any view or query. [More](/crosswalker/agent-context/zz-log/2026-06-04-data-morphology/) |
| <span id="lens"></span>**Lens** | A subgraph of the vault read for one purpose. General capability; the GRC application is the Control / Assurance / Risk lenses of the [Unified Risk Model](/crosswalker/agent-context/zz-log/2026-06-04-urm-questions-data-morphology/). |
| <span id="crosswalk"></span>**Crosswalk** | An edge where **both ends are ontology concepts**: *"these two correspond."* `NIST 800-53/AC-2` ↔ `ISO 27001/A.9.2.1`, or a framework mapped onto a [synthetic spine](/crosswalker/agent-context/zz-challenges/archive/06-synthetic-spine/). Committed edge vocabulary: [STRM](/crosswalker/reference/registry/strm/) predicates inside an [SSSOM](/crosswalker/reference/registry/sssom/) envelope. [Diagram](/crosswalker/concepts/mapping-into-obsidian/#edge-models) · [interlingua pattern](/crosswalker/concepts/schema-matching/#the-interlingua--pivot-approach) |
| <span id="crosswalk-column-role"></span>**Crosswalk column role** | *A source column that says which concepts in another framework each row maps to.* The import wizard offers this role and lets the user name the target framework and relationship. Generation [reifies](#reification) each cell as separate [Crosswalk](#crosswalk) edge notes rather than as concept-note frontmatter. Machine contract: [`target.crosswalks[]` in schema spec §4.13](/crosswalker/agent-context/v0-1-schema-spec/#target-crosswalks). |
| <span id="nested-record-level"></span>**Nested record level** | *One record type that lives inside another in the source, such as controls inside groups.* Each emitted row carries its lineage in the reserved `_cw` object: its level, root-first identity path, immediate parent, and carried ancestor fields. Machine contract: [`source.nest[]` in schema spec §4.15](/crosswalker/agent-context/v0-1-schema-spec/#source-nest). |
| <span id="section-record"></span>**Section record** — *also:* body projection of a nested level | *A nested record written as a heading with text inside its parent's note, not as a note of its own.* A nest level declaring `leaf: section` attaches each record to its nearest emitted ancestor; the record renders as a heading region inside that note's managed body and gets no note, CURIE, provenance, Tier 2 row, or orphan tracking, because it is content of its host concept, not a concept. Chosen in the wizard with **Below the note** or a nested row's **Placement**. Machine contract: [`leaf: section` in schema spec §4.16](/crosswalker/agent-context/v0-1-schema-spec/#nest-section). |
| **Evidence link** — *also:* implementation link, junction note, link metadata, dotKey metadata (legacy) | An edge from a **user-authored document to an ontology concept**: *"this note attests to that concept, at such-and-such status."* **Not a crosswalk.** Stored as **junction notes** — one markdown file per edge, 13-field flat YAML isomorphic to [OSCAL](/crosswalker/reference/registry/oscal/)'s `by-component`, with three orthogonal status dimensions (`status` · `freshness` · `evidence_type`); git history is the audit trail. [Decision log](/crosswalker/agent-context/zz-log/2026-04-10-evidence-link-edge-model-synthesis/) · [Challenge 07](/crosswalker/agent-context/zz-challenges/archive/07-link-metadata-edge-model/) · [diagram](/crosswalker/concepts/mapping-into-obsidian/#edge-models). Supersedes the inline-field [link metadata system](/crosswalker/agent-context/link-metadata-system/). |
| **Typed link** | Umbrella term for any link carrying relationship metadata. Covers both crosswalks and evidence links. |
| <span id="endpoint"></span>**Endpoint** | The two things at either end of a relationship — in "MFA-Policy implements AC-2," the policy and the control are the endpoints. The shipped contract keeps clickable addresses separate from stable identity: concept hierarchy uses `parent` + `parent_curie`; junction notes use `subject`/`object` + optional `subject_curie`/`object_curie`; crosswalk edges use identity CURIEs directly. [Identity decision](/crosswalker/agent-context/zz-log/2026-08-21-reimport-is-identity-reconciliation/) |
| <span id="facet-note"></span>**Facet note** | A generated index note collecting every concept that shares one property value — in a GRC vault, all controls carrying a given theme tag. Carries `kind: facet` and a members list of wikilinks. Emitted by import enrichment (source: `src/generation/enrich.ts`) when facet hubs are enabled. Honest status: these notes are written by the generator but have no branch in the [note contract](#schema-contract) yet and skip validation — closing that gap is open decision [P4](/crosswalker/agent-context/zz-log/2026-07-25-owner-review-queue/#p4--validate-the-two-note-kinds-that-currently-skip-validation). |
| <span id="implied-concept"></span>**Implied concept** — *a first-class thing named inside other rows, without a row of its own* | A source may encode an upper-level concept only as an identifier prefix in its child records. The recipe can make that level an addressable concept note with its own stable CURIE, provenance, children, and parent links, rather than a [hub note](#hub-note). [Recipe contract §4.17](/crosswalker/agent-context/v0-1-schema-spec/#implied-concepts). |
| <span id="hub-note"></span>**Hub note** — *also:* level hub | A generated table-of-contents note for one folder level, listing that folder's direct children as wikilinks. Carries `kind: hub`. Emitted by import enrichment (source: `src/generation/enrich.ts`) when level hubs are enabled. Same contract gap and same open decision [P4](/crosswalker/agent-context/zz-log/2026-07-25-owner-review-queue/#p4--validate-the-two-note-kinds-that-currently-skip-validation) as facet notes. |
| **Hierarchy column** | A source column whose values define nesting levels. |
| **Frontmatter** | YAML properties at the top of a markdown note. Obsidian calls them *properties*. |
| **Fingerprint** | A hash of a data file's structure, used to match a source against saved configs. |

## Data flow and implementation terms

Objects that support editors and runtimes. They do **not** become first-class artifacts merely by being persisted or passed between functions.

| Term | Definition |
|------|-----------|
| **ParsedData** | Parser output: columns plus eager or streamed rows. Not a tier, not a contract. |
| **ColumnInfo** | Analysis of one source column — type, unique count, samples. |
| **CrosswalkerConfig** | Legacy full import configuration shape. Not the portable [Recipe](#recipe) authority. |
| **SavedConfig** | Legacy fingerprint-bound wizard convenience state in plugin settings. May restore a past mapping; is not an [ImportRecipe](#import-recipe), a Recipe binding, or a share/open lifecycle. |
| **WizardDraft** | Resume state for an unfinished interaction. Workflow state, not a Recipe or [Execution Record](#execution-record). |
| **RecipeDocument** | The preservation/editor transaction boundary: original validated ImportRecipe + editable [ImportMapping](#import-mapping) + session-only origin/dirty state. It *patches* workbench-owned regions into the original rather than rebuilding it and dropping opaque fields. [More](/crosswalker/agent-context/zz-log/2026-07-21-portable-import-recipe-fidelity-synthesis/) |
| **GeneratedNote**, **Address**, **RenderedBodyRegion**, **RenderReport**, **GenerationResult** | Runtime results and diagnostics produced while applying a Recipe. Not separately governed artifacts. |

## Ontology evolution terms

Owning pages: [ontology evolution](/crosswalker/concepts/ontology-evolution/) · [framework versioning](/crosswalker/concepts/framework-versioning/).

| Term | Definition |
|------|-----------|
| **Ontology evolution** | How a knowledge system changes over time — concepts added, removed, restructured. Distinct from *versioning* (which release you have). [More](/crosswalker/concepts/ontology-evolution/) |
| **Schema evolution** | Changes to the *structure* of data (fields added, columns renamed) rather than to the data itself. |
| **Deprecation chain** | A sequence of `revoked-by` links from old concepts to their replacements. MITRE ATT&CK does this with STIX 2.1. [More](/crosswalker/concepts/framework-versioning/#mitre-attck--the-gold-standard) |
| **SemVer** | MAJOR.MINOR.PATCH. OSCAL guarantees content valid under a MAJOR version stays valid in later releases of it. [More](/crosswalker/concepts/ontology-evolution/#schemaver-an-alternative-to-semver-for-data) |
| **SchemaVer** | MODEL-REVISION-ADDITION versioning for data (Snowplow). MODEL = can old consumers read new data? REVISION = the reverse? ADDITION = non-breaking. [More](/crosswalker/concepts/ontology-evolution/#schemaver-an-alternative-to-semver-for-data) |
| **SCD (Slowly Changing Dimensions)** | Warehouse pattern for records that change over time: Type 1 overwrite · Type 2 keep history · Type 3 alias column · Type 6 hybrid. [More](/crosswalker/concepts/ontology-evolution/#how-data-warehouses-handle-this-slowly-changing-dimensions) |
| **[SKOS](/crosswalker/reference/registry/skos/)** | Simple Knowledge Organization System (W3C). Natural fit on paper — ConceptScheme = framework, broader/narrower = hierarchy — but its 5 predicates carry no confidence, provenance, or negation, so it was **rejected as the crosswalk base**. [Why](/crosswalker/agent-context/zz-log/2026-04-10-foundation-research-synthesis/#edge-semantics-should-be-set-theoretic-not-skos-ish) |
| **[SSSOM](/crosswalker/reference/registry/sssom/)** | Simple Standard for Sharing Ontological Mappings. The **row-schema envelope** for crosswalk edges: required `mapping_justification` plus optional `confidence`, `author_id`, `mapping_date`, `mapping_tool`, `predicate_modifier`. Predicate-agnostic — you supply the vocabulary (see STRM). [More](/crosswalker/concepts/schema-matching/#sssom-a-standard-for-sharing-mappings) |
| **[STRM](/crosswalker/reference/registry/strm/)** — Set Theory Relationship Mapping | The 5-relationship edge vocabulary — **equivalent-to · subset-of · superset-of · intersects-with · no-relationship** — that [NIST IR 8477](https://csrc.nist.gov/pubs/ir/8477/final), [SCF](/crosswalker/reference/registry/scf/), and OSCAL's Control Mapping Model converged on independently. Crosswalker's `predicate_id` vocabulary, paired with SSSOM as envelope. [More](/crosswalker/concepts/schema-matching/#nist-olirs-formal-relationship-types) |
| **OSCAL** | Open Security Controls Assessment Language (NIST). Machine-readable controls with built-in versioning; also adopts STRM in its Control Mapping Model. [Registry](/crosswalker/reference/registry/oscal/) |
| **[OLIR](/crosswalker/reference/registry/olir/)** | Online Informative References (NIST) — a submission-based crosswalk registry using the same STRM relationship types. [Registry](/crosswalker/reference/registry/olir/) |
| **Interlingua / pivot** — *also:* pivot ontology, synthetic spine, hub-and-spoke mapping, meta-framework | One "universal" framework everything else maps through, like a pivot language in translation. Map to [SCF](/crosswalker/reference/registry/scf/) once, get crosswalks to 175+ frameworks. The five names are the same pattern from five disciplines. Open question: [Challenge 06](/crosswalker/agent-context/zz-challenges/archive/06-synthetic-spine/) · [more](/crosswalker/concepts/schema-matching/#the-interlingua--pivot-approach) |

## Architecture & evolution primitives

From the [Foundation phase](/crosswalker/reference/roadmap/) research. Each carries aliases that appear across the knowledge base.

| Term | Aliases | Definition |
|------|---------|-----------|
| **Ontology diff primitives** | Graph change atoms, structural change primitives, structural diff engine | The [9 provably complete atomic operations](/crosswalker/agent-context/zz-log/2026-04-09-atomic-operations-research/) describing what changed between two versions of a labeled directed graph — the mathematical answer to "what changed?" (graph edit distance, algebraic graph transformation). |
| **EvolutionPattern** | Framework handling profile, stewardship profile, evolution taxonomy | Per-framework classification of *how* an ontology evolves; sets defaults for [handling strategies](/crosswalker/agent-context/zz-log/2026-04-09-user-first-ontology-maintenance/#step-3-decision). **Open:** may be replaced by [transformation recipes](/crosswalker/agent-context/zz-log/2026-04-09-primitives-depth-and-pluggable-layers/). |
| **Transformation recipe** | Version transition map, migration spec | The record of what changed between two specific versions and how to handle each change — "NIST r5→r6: AC-19(2) merged into AC-19, AC-24 added." |
| **Handling strategy** | — | What to do when a change type is detected: overwrite, archive, alias, merge, split, skip, or flag for review. |
| **Decisioning** | Strategy selection | Choosing handling strategies per change type — by default, per framework, or per user/org. [Layered model](/crosswalker/agent-context/zz-log/2026-04-09-primitives-depth-and-pluggable-layers/#thread-4-decisioning-as-per-framework-taxonomy-taxonomy-over-taxonomies) |
| **Pluggable layer** | Extension point, opinionated layer | Any behavior that is opinionated and swappable rather than first-principles. Keeps the system [tight to first principles while allowing extension of opinionation](/crosswalker/agent-context/zz-log/2026-04-09-user-first-ontology-maintenance/#the-first-principles-constraint). |
| **Progressive depth** | Progressive complexity | Start with guided UI, graduate to config-as-code, add CLI — each interface wrapping the same core primitives. Applies to [import](/crosswalker/features/import-wizard/) and [migration](/crosswalker/agent-context/zz-log/2026-04-09-user-first-ontology-maintenance/) alike. |
| **Entity** | User, agent | Any actor using the system — [people or agents](/crosswalker/agent-context/zz-log/2026-04-09-user-first-ontology-maintenance/#the-entities). Both must be first-class. |

## Data model terms

Owning pages: [file-based graph database](/crosswalker/concepts/file-based-graph-database/) · [consistency models](/crosswalker/concepts/consistency-models/).

| Term | Definition |
|------|-----------|
| **Property graph** | A graph where both nodes and edges carry key-value properties. An Obsidian vault is one: notes = nodes, wikilinks = edges, frontmatter = properties. [More](/crosswalker/concepts/file-based-graph-database/#property-graph-model) |
| **Edge metadata** — *also:* link metadata, typed link metadata, inline field metadata, dotKey metadata | Structured data attached to the *relationship* between two notes rather than to either note. The umbrella data-model concept behind both [crosswalks](#core-terms) and [evidence links](#core-terms); both now have committed shapes. [Diagram](/crosswalker/concepts/mapping-into-obsidian/#edge-models) |
| **Denormalization** | Deliberately duplicating data to make reads fast at the cost of write complexity — e.g. storing both forward links and frontmatter arrays. [More](/crosswalker/concepts/file-based-graph-database/#the-denormalization-tax) |
| **Referential integrity** | The guarantee that every link points at something that exists. Obsidian vaults have **none** — delete a note and the links stay broken. [More](/crosswalker/agent-context/constraint-enforcement/#the-referential-integrity-gap) |
| **ACID** | Atomicity, Consistency, Isolation, Durability. File-based systems give you only Durability. [More](/crosswalker/concepts/consistency-models/#acid-analysis-for-file-based-systems) |
| **CAP theorem** | A distributed system gets at most two of Consistency, Availability, Partition tolerance. Vaults are AP. [More](/crosswalker/concepts/consistency-models/#cap-theorem-positioning) |
| **Eventual consistency** | Copies converge given enough time. In Crosswalker, re-import achieves it — but you have to run it. [More](/crosswalker/concepts/consistency-models/#base-model) |
| **Event sourcing** | Storing the sequence of changes rather than only the current state. A future `_crosswalker.history` field would enable it. [More](/crosswalker/concepts/consistency-models/#event-sourcing-pattern) |

## Matching & alignment terms

Owning page: [schema matching](/crosswalker/concepts/schema-matching/).

| Term | Definition |
|------|-----------|
| **Schema matching / schema alignment / ontology matching / ontology alignment / crosswalking / data integration / framework mapping** | *Seven names for one broad concept:* finding correspondences between elements of different structured datasets. Each name comes from a different discipline — databases, semantic web, library science, ETL, GRC. Within one field they have precise distinct meanings ([distinctions table](/crosswalker/concepts/schema-matching/#terminology-distinctions)); Crosswalker straddles all of them, so which name a page uses depends on which community it's drawing from. |
| **Schema matching** (narrow) | Database sense: finding corresponding *elements* (columns, fields, keys) between schemas. Crosswalker's column-type detection is a simple case. |
| **Schema mapping** (narrow) | The executable *transformation* implementing a match — "split column A by comma, map each into column B." |
| **Ontology alignment** (narrow) | Semantic-web sense: finding corresponding *concepts* with confidence scores. "AC-2 corresponds to CIS 5.2 at 0.85" is ontology alignment. |
| **Ontology merging** | Combining two ontologies into one. SCF folding 175+ frameworks into a single canonical set is the example. |
| **Crosswalk edge semantics stack** | Crosswalker's layered commitment: [STRM](/crosswalker/reference/registry/strm/) as the required predicate vocabulary + [SSSOM](/crosswalker/reference/registry/sssom/) as the required envelope + [SKOS](/crosswalker/reference/registry/skos/) rejected as base but kept as an export format. [Decision](/crosswalker/agent-context/zz-log/2026-04-10-foundation-research-synthesis/#edge-semantics-should-be-set-theoretic-not-skos-ish) |
| **OAEI** | Ontology Alignment Evaluation Initiative — the annual benchmark for alignment algorithms. Recent LLM-based systems hit 0.83–0.95 F1. [More](/crosswalker/concepts/schema-matching/) |
| **Formal Concept Analysis** | Lattice-theory approach to finding structural correspondences between hierarchies without string similarity. Candidate for [spine distillation](/crosswalker/agent-context/zz-challenges/archive/06-synthetic-spine/). [More](/crosswalker/concepts/schema-matching/#formal-concept-analysis-fca) |

## Query engine — three layers

The query engine keeps three orthogonal layers apart (settled 2026-05-08; [synthesis](/crosswalker/agent-context/zz-log/2026-05-07-bases-query-layer-architecture-synthesis/)):

| Layer | What it is | Concept page |
|---|---|---|

## Query language & engine terms (engine internals)

Recurring in the [Tier 2/3 engine research wave](/crosswalker/agent-context/zz-log/2026-05-02-direction-third-wave-architectural-shifts/). Quick reference only.

| Term | Definition |
|------|-----------|
| **[Datalog](/crosswalker/concepts/zz-glossary/datalog/)** | Declarative logic programming — write *rules* (`derived(a,c) :- mapping(a,b), mapping(b,c)`) and the engine derives all consequences. "SQL with built-in recursion." Used for **SSSOM chain rules**; engine choice is [Nemo](/crosswalker/agent-context/zz-research/2026-05-02-challenge-12-deliverable-a-datalog-vs-sql/). [Verbose entry](/crosswalker/concepts/zz-glossary/datalog/) |
| **SPARQL** | The W3C query language for RDF — the SQL of the semantic web. Native fit for SSSOM (which is RDF-shaped); supports federation via `SERVICE`. |
| **Recursive CTE** | SQL's `WITH RECURSIVE` for transitive closure and graph walks. The fallback when Datalog isn't available; tractable to ~10⁵ mappings, collapses on full SSSOM expressivity. [Ch 18](/crosswalker/agent-context/zz-challenges/archive/18-tier-2-lite-sssom-rule-subset/) |
| **Stratified negation** | Datalog's ability to negate another layer's conclusions in a defined order — "find A→C mappings NOT derivable through any intermediate B." Recursive CTE can fake it; Datalog optimizes it natively. |
| **SPARQL property paths** | Recursive operators inside SPARQL (`?x (skos:exactMatch)+ ?y`). Datalog-lite: no stratified negation, no rule-level aggregation. [Ch 14](/crosswalker/agent-context/zz-research/2026-05-02-challenge-14-missed-engines/) |
| **OWL inference** | Reasoning that derives implicit class/property relationships. Crosswalker does not currently rely on it. |
| **SHACL** | Shapes Constraint Language — W3C standard for *validating* RDF graphs ("every mapping_set MUST have a creator_id"). Used for SSSOM validation at the Tier 2/3 boundary. |
| **WOQL** | TerminusDB's Datalog dialect (`path()`, `dot()`, `slice()`). Relevant only if [TerminusDB is adopted](/crosswalker/agent-context/zz-research/2026-05-02-challenge-16-tier-3-reconsideration/). |
| **HDT** | Header-Dictionary-Triples — binary RDF distribution format, ~10–20× smaller than Turtle. Used by Comunica federation. |

## Metadata ecosystem terms

Owning page: [metadata ecosystem](/crosswalker/concepts/metadata-ecosystem/).

| Term | Definition |
|------|-----------|
| **Inline field** | Legacy `key:: value` syntax in a note body. Not queryable by Bases; Crosswalker uses YAML properties and explicit edge records instead. |
| **Properties** | Obsidian's native YAML frontmatter system (since v1.4). First-class and Bases-queryable. |
| **Obsidian Bases** | Native `.base` live views over vault properties. Bases filters and presents frontmatter; it does not by itself do multi-hop typed-edge traversal. [More](/crosswalker/concepts/metadata-ecosystem/) |
