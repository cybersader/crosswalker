A vault can be built entirely outside Obsidian and still be fully operational once the plugin opens it. No separate tool is needed beyond what already ships: the `cw` command line and the demo builder.

**Status last verified:** 2026-10-30 — private-demo section checked against `scripts/demo-add-licensed.mjs`, the generic referenced-framework adapter and two byte-identical private CRI/CIS/SCF runs. Other sections retain their 2026-10-29 verification against `package.json` (`cw`, `demo:build` scripts), `cli/crosswalker.ts`, `cli/fs-app.ts`, `scripts/demo-build.mjs`, `src/tier2/projector.ts`, `src/tier2/sidecar.ts`, `src/import/import-set-recipes.ts`, `src/generation/import-set.ts`, `src/mappings/mapping-set.ts`, `src/views/reference-base-files.ts`, `src/main.ts` (status bar), `src/discovery/installed-frameworks.ts` and `src/graph/graph-color-command.ts` (both merged in PR #67).

<Aside type="tip" title="The question this page answers">
"Do we need a Crosswalker CLI to realistically go from files to upload in OpenClast, or moving files into Obsidian, to having something operational? Is it possible to do all the work outside the plugin, or if you import then things aren't going to be quite right?"

**Answer:** no new tool. Build on disk with `cw`, open or upload the folder, and the plugin rebuilds everything else from the notes. Where something is not quite right after that, it is a plugin bug against the invariant below, not a reason to import through the wizard.
</Aside>

The [UI and CLI parity reference](/crosswalker/reference/ui-cli-parity/) distinguishes shared engine behavior from actions not yet exposed by `cw`. It tracks both directions with explicit reasons and plans. The CLI is not yet a full replacement for every plugin action; in particular saved-query creation, approvals and recipe-library management remain tracked gaps.

## 1. Why this works: the schema is the contract

[Architectural commitment 1, schema-as-primitive](/crosswalker/concepts/etl-and-import/#the-reframe--schema-is-the-primitive-etl-is-convenience): the [Tier 1](/crosswalker/concepts/terminology/) (canonical Markdown notes with frontmatter) contract in the [v0.1 schema spec](/crosswalker/agent-context/v0-1-schema-spec/) is load-bearing. Any producer that writes valid Tier 1 notes is first-class. The import wizard is one producer among several.

| Producer | What it is | Same engine as the plugin? | Source |
|---|---|---|---|
| Import wizard | The plugin's in-Obsidian import modal | Yes (it is the plugin) | `src/import/import-wizard.ts` |
| `bun run cw` | Command line with 6 commands: `import`, `validate`, `export`, `replay`, `recipes`, `graph` (source: `cli/crosswalker.ts` `runCli` switch) | Yes. Runs the plugin's own `src/` code against a plain folder through a filesystem stand-in for the Obsidian `App` | `cli/crosswalker.ts`, `cli/fs-app.ts` |
| `bun run demo:build` | Builds the multi-framework demo vault | Yes. Every Crosswalker note is written by spawning the `cw` entry point, never by calling the engine directly; the build ends with `cw validate` | `scripts/demo-build.mjs` |
| Any external producer | A script, agent or other tool that emits valid Tier 1 | Not required; validity against `spec/tier1.schema.json` is the bar | [ETL pillar](/crosswalker/concepts/etl-and-import/) |

## 2. What is identical, what is derived, what is host config

| Layer | Examples | Produced outside Obsidian? | Source |
|---|---|---|---|
| **Tier 1 content (identical)** | Concept notes, frontmatter, folders, typed wikilinks | Yes, `cw import` runs the same generation engine | `cli/crosswalker.ts` (`runRecognizedImport`), `cli/fs-app.ts` |
| | Import-set ownership (the minted set id stamped in each note's `_crosswalker` provenance; the provenance is the registry, no separate file) | Yes | `src/generation/import-set.ts` header |
| | Recipe copy per run, `_crosswalker/import-sets/<set id>/recipe-<digest>.json` | Yes, written through `vault.adapter` | `src/import/import-set-recipes.ts`, `cli/fs-app.ts` |
| | Mapping notes plus the mapping-set release record (`kind: mapping-set`) | Yes, `cw import` of a `.sssom.tsv` runs `importSssom` | `cli/crosswalker.ts`, `src/import/sssom-importer.ts`, `src/mappings/mapping-set.ts` |
| **Derived at runtime (rebuilt by the plugin)** | [Tier 2](/crosswalker/concepts/embedded-vs-server-substrates/) query database (plain: the SQLite index behind queries), a projection of Tier 1 | Never needed. Lives in the plugin's private browser storage (OPFS), not in the vault, and the projector rebuilds it from Tier 1 on vault load | `src/tier2/projector.ts` header ("rebuilds it from canonical Tier 1"), `src/tier2/sidecar.ts`, `src/main.ts` (`autoProjectOnLayoutReady`) |
| | Reference query files (Coverage Matrix `.base`, `_crosswalker/SKILL.md`) | Not needed. Written on first plugin run if absent, never overwritten | `src/views/reference-base-files.ts` |
| | Status bar framework count and installed frameworks list | Not needed. Discovery by note identity across the whole vault, refreshed on metadata cache events, and shown as indexing until the cache is ready (`src/discovery/installed-frameworks.ts`, merged in PR #67) | `src/main.ts` (status bar), PR #67 |
| **Vault/app config (not carried by every host)** | `.obsidian/graph.json` graph colors | `demo:build` writes it, and nothing else under `.obsidian`. OpenClast rooms do not carry `.obsidian` (reported in PR #67). The command "Color the graph by framework" (merged in PR #67) recreates it per vault from the frameworks present | `scripts/demo-build.mjs`, `tools/lib/demo-graph.ts`, PR #67 |
| | Plugin settings (Obsidian's per-plugin data file) | Imports run on `DEFAULT_SETTINGS`. Graph configuration reuses the existing plugin data file for exact color ownership snapshots, preserving unrelated settings; a fresh plugin otherwise starts on defaults | `cli/crosswalker.ts`, `cli/graph.ts`, `src/graph/graph-configuration.ts`, `src/main.ts` (`loadSettings`) |

## 3. The invariant

> **The plugin derives every runtime surface from note identity. Never from state only the import wizard writes, and never from paths.**

| Clause | Why | Precedent |
|---|---|---|
| From note identity | Notes are the only thing every producer and every host share | [Identity reconciliation](/crosswalker/agent-context/zz-log/2026-08-21-reimport-is-identity-reconciliation/) |
| Not from wizard-only state | A `cw`-built or uploaded vault has no plugin data and no wizard history | This page |
| Not from paths | Folder shape is a recipe choice and changes across producers; three bugs came from inferring meaning from vault paths | [First run and the blind spots that hid it](/crosswalker/agent-context/zz-log/2026-08-28-first-run-and-the-blind-spots-that-hid-it/) |
| Not before indexing | An unindexed note is not an absent note; say "indexing", never zero | PR #67 status bar |

**Worked example, 2026-10-29.** In a vault built by `cw` or `demo:build`, the status bar read "Crosswalker: no frameworks yet" (`src/ui/entry-points.ts`). Two causes, both violations of the invariant: discovery looked only under the output-folder setting (a path the CLI-built frameworks were not under), and it refreshed on file events that fire before Obsidian has indexed the notes. PR #67 moves discovery to note identity across the vault and refreshes on metadata cache events.

The existing guard for the empty-vault case is `tests/e2e/first-run.spec.ts`, the only spec that starts from a vault with no seed notes and no plugin data. Nothing yet starts from a `cw`-built vault (see § 5).

## 4. Three paths to an operational vault

| Path | Steps | What the plugin does on open | Caveats |
|---|---|---|---|
| **A. Wizard in Obsidian** | Open a vault, run "Start here: import structured data" (source: `src/main.ts`) | Projects Tier 2, writes reference queries, counts frameworks | None specific |
| **B. On disk, then Obsidian** | `bun run cw -- import --vault <dir> --source <file> ...` (or `bun run demo:build -- --out <dir>`), then `cw validate`, then open the folder as a vault | Same as A, from the notes | Graph colors: `demo:build` writes `.obsidian/graph.json`; for other `cw` vaults run the graph color command |
| **C. On disk, then OpenClast** | Build as in B, then push the folder into an OpenClast room with OpenClast's own vault push tooling. OpenClast hosts real Obsidian in a browser tab, so the same plugin runs | Same as A, from the notes | Dot-folders are not uploaded, so per-vault app config (`.obsidian/graph.json`, plugin settings) does not arrive. The plugin must recreate it: graph colors or explicit overview by command, settings from defaults |

## Graph display: preserve first, overview by choice

**Graph behavior last verified:** 2026-10-30 against `src/graph/graph-colors.ts`, `src/graph/graph-color-command.ts`, `src/graph/graph-configuration.ts`, `cli/graph.ts` and synthetic regression tests. Other verification scopes on this page remain separately dated.

**Color the graph by framework** changes only colors. Your search (including an intentionally empty search), visibility choices, forces, camera, panels and unknown options remain unchanged. Missing display settings stay missing. Custom rules keep their order and precedence, even when their query exactly matches a generated rule. Only an unchanged, exact previously emitted occurrence is replaceable; query-only legacy markers are not ownership proof. Ownership snapshots live in the existing plugin data file, not in [Tier 1 content](/crosswalker/agent-context/v0-1-schema-spec/).

**Configure framework graph** opens an explicit, cancelable preview of saved global defaults. The initial overview patch has **four settings (source: `src/graph/graph-colors.ts`, `frameworkOverviewPatch`)**: tag nodes off, attachment nodes off, native file-link arrows off, line thickness 1.3. Tags remain in notes. Arrows describe native file links, not mapping predicates, equivalence or transitivity. Search, unresolved visibility, orphan visibility, forces and camera are preserved. Applying also explicitly refreshes colors; your custom colors still win.

Close global graph views before applying in the plugin: open views can save their private settings over global defaults. The command blocks rather than closing or overwriting those views. With global views closed, it reloads the complete authoritative saved defaults into the native global cache, including removing stale cache-only keys. Native Graph supplies missing defaults when a new view opens. If that cache cannot reload safely, the command reports partial application and asks you to restart Obsidian before opening Graph view, not silent success. Reopen the global graph afterward. Local graphs are untouched. This is a quieter overview, not a claim that the entire network is readable. Focused **Connections** and readable mapping filenames are deferred; no note identity, recipe, mapping assertion or existing filename changes in this slice.

The [UI/CLI parity reference](/crosswalker/reference/ui-cli-parity/) records both routes. The CLI uses the same policy; preview is the default:

```bash
bun run cw -- graph configure --vault ./demo --mode overview
```

Close Obsidian before adding `--apply`. Omit `--mode` for colors only; `--config-dir <vault-relative-folder>` selects another config directory. Both graph settings and existing plugin data must be readable objects before any writes. Previews expose only a supported display-change summary, never custom searches, color queries or unrelated plugin data. If color-history persistence fails after graph settings were written, the command reports partial application rather than claiming success or rolling back unrelated settings.

Fresh demo generation explicitly initializes the overview with its administrative search and new-view camera defaults. Augmentation reads the actual existing graph document and merges colors only; it never replaces existing display choices with fresh defaults. Only a genuinely absent document gets initialization. These paths are tested with synthetic settings, without rebuilding licensed sources. Preservation is measured immediately before and after Crosswalker's action: native Graph can independently normalize opacity, discard unsupported keys and supply defaults when it later saves. The native regression records that boundary separately from our write, including an external disk edit that deliberately leaves the native cache stale.

## Private demo: two separate steps

The public build remains repository-safe. A separate, explicit add-on enriches a fresh copy with locally held CRI Profile 2.2, CIS Controls 8.1 and SCF 2026.1.1, CRI subject tags, and publisher mapping releases whose endpoints exist in that vault. SCF also adds selected identifier-only referenced frameworks, direct source/target links, a framework-reach Bases query and distinct graph colors. The workflow rewrites the welcome note to list what was actually added. Obtain the files yourself and check their terms; the [acquisition and binding reference](/crosswalker/reference/framework-data-sources/#private-room-demo-add-on) lists every expected filename, worksheet and exclusion rule.

Run these separately from the checkout:

```bash
bun run demo:build -- --out /tmp/cw-private-demo
```

```bash
bun run demo:add-licensed -- --private-room-only --vault /tmp/cw-private-demo
```

Use `--sources-dir <source-checkout>` when licensed files are held in another checkout; relative manifest paths resolve there without copying sources into this checkout. `--only cri`, `--only cis` or `--only scf` selects one framework; `--source <workbook>` is valid only with one explicit `--only` key and changes only that framework source, not mapping paths. Missing files are skipped with acquisition guidance. The output must be outside the repository, must contain no symlinks and must start from a fresh demo without the selected licensed frameworks. If a run fails or is interrupted, discard that output and repeat on a fresh public base.

**Private-room-only means private.** The acknowledgement does not grant redistribution rights. Do not publish the enriched vault or use the public demo distribution path for it. For OpenClast, use a private room only after confirming that its audience and use fit the source terms. No upload is performed by this script.

**Verification scope, 2026-10-30:** the add-on and explicit mapping-release isolation were checked through CLI tests, local authorized workbook runs, final note validation and two byte-identical output trees, including hidden graph settings (sources: `scripts/demo-add-licensed.mjs`, `tests/cli/demo-add-licensed.test.ts`, `tests/cli/mapping-release-isolation.test.ts`). The [source reference](/crosswalker/reference/framework-data-sources/#resolution-and-release-limits) records aggregate results and unresolved endpoint reasons. This does not re-verify the unrelated runtime surfaces listed above.

**UI parity gap:** this ordered private-demo orchestration and its cross-sheet subject-tag join are CLI-only; no dedicated in-plugin action runs the manifest. The ordinary import UI and mapping import UI remain available for individual imports. This tooling slice does not claim that the private workflow has UI parity.
