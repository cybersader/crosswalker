<Aside type="tip" title="What this page is">
The **picture-first** overview of the whole system. Every box below links to the page that explores it in depth.

The model is **domain-neutral**: Crosswalker represents an *ontology* — a set of concepts and the typed relationships between them — as canonical, queryable Markdown. Compliance frameworks are the launch use case, not the model; where something is compliance-specific it's flagged as such. For the detailed reference (component-to-tier matrix, read/write flows), continue to [system architecture](/crosswalker/concepts/system-architecture/).
</Aside>

## Your data goes in, answers come out

Crosswalker takes whatever shape your data ships in — a control spreadsheet, a crosswalk export, a JSON ontology — and turns it into **ordinary Markdown notes in your vault**. Then it makes those notes answerable. Everything else on this page is detail on that one spine:

Most people use **Door A** (the wizard). **Door B** exists for automation, bulk runs, and agents. **In the formal vocabulary:** the ImportRecipe is a [Recipe](/crosswalker/concepts/terminology/#recipe) artifact *adjacent* to generation — its Recipe [Schema Contract](/crosswalker/concepts/terminology/#schema-contract) governs the instruction, and the Tier 1 Schema Contract governs the generated records. The recipe is never stored inside the vault as ontology content.

## What's the real copy, and what's just a cache

The single most important rule: **the Markdown in your vault is the real thing.** Everything else is either upstream of it or rebuilt from it. Here's an actual note it produces:

- **The rules are written down, not implied** — a [Schema Contract](/crosswalker/concepts/terminology/#schema-contract) governs what a valid note looks like, and a separate one governs what a valid recipe looks like.

## One row in, one note out <span id="from-source-to-structure--render--the-5-mechanisms"></span>

This is the engine room. You give it two things and it hands back a finished note — *where* it lives and *what's written* in it:

- **one record** — a row from your source, pinned to a stable id. Below it's a biological species; it could just as easily be a security control, a product, or a city. (Formally: a [ConceptIdentity](/crosswalker/concepts/terminology/#conceptidentity).)
- **your rules** — which source field becomes the folder, the filename, the tags, the properties, the links. (Formally: an [ImportRecipe](/crosswalker/concepts/terminology/#import-recipe).)

The function that does it is [`render()`](/crosswalker/concepts/terminology/#render) — one pure function, `render(Recipe, ConceptIdentity) → Address`, and the only place layout decisions live.

Anything past the closed filters (conditionals, lookups, concatenation) escapes the same way.

## The readers — one per shape your data arrives in <span id="the-ingest-tools"></span>

A reader is a *front-end* to `render()`, never a second engine — and the same readers back the wizard's parsers (*one reader, two doors*). Between them they produce the only two things a vault holds: **concepts** (the notes) and **relationships** (the links between them):

| Source shape | What a reader does | Produces |
|---|---|---|
| **Flat table** — rows in a CSV or spreadsheet | one row → one concept | concept notes |
| **Nested document** — records inside a tree (JSON, at an iterator path) | one record → one concept | concept notes |
| **Mapping table** — one source id against many target ids | each pair → one typed edge | relationship (crosswalk) notes |

The *shapes* are general. The current named implementations in `tools/` — `generate-fixtures` plus the `crosswalk-from-*` extractors — happen to target the compliance launch corpus; see the [ingestion dev log](/crosswalker/agent-context/zz-log/2026-06-02-ingestion-tooling-dev/) for those specifics and the [readiness board](/crosswalker/agent-context/zz-log/2026-06-12-urm-ingestion-readiness/) for status.

## Four words that get mixed up

Crosswalker's vocabulary describes four different dimensions. Keeping them separate stops a Recipe, a Tier, a layer, and a lifecycle capability being read as the same kind of thing.

| Dimension | Question answered | Examples |
|---|---|---|
| **[Artifact role](/crosswalker/concepts/artifact-roles-and-authority/)** | What kind of governed thing is this? | [Schema Contract](/crosswalker/concepts/terminology/#schema-contract) (the rules); [Knowledge Set](/crosswalker/concepts/terminology/#knowledge-set) (the content); [Recipe](/crosswalker/concepts/terminology/#recipe) (the instructions); later [Execution Record](/crosswalker/concepts/terminology/#execution-record) and [Package Manifest](/crosswalker/concepts/terminology/#package-manifest) |
| **[Representation tier](/crosswalker/concepts/terminology/#tiers)** | Where does knowledge live, and which copy wins? | Tier 0 source; Tier 1 canonical Markdown; Tier 2 derived SQLite cache |
| **Logical layer** | Which part of the system is doing the work? | Import, storage, projection, query, export, audit |
| **[Lifecycle capability](/crosswalker/concepts/ontology-lifecycle/)** | What is the user actually trying to do? | Acquire, Shape, Connect, Understand, Share, Maintain |

Tier 1 is therefore a **representation and authority tier**, not the root artifact. The [ImportRecipe](/crosswalker/concepts/terminology/#import-recipe) sits *beside* generation: its Recipe Schema Contract governs the instruction, the Tier 1 Schema Contract governs the generated records.
