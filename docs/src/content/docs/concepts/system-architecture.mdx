## TL;DR

Crosswalker has **three representation/storage tiers** and **six logical layers** that move data between them. These are independent of [artifact role](/crosswalker/concepts/artifact-roles-and-authority/) and [lifecycle capability](/crosswalker/concepts/ontology-lifecycle/). For the *convention* view of the same stack — the named DSL at each layer, built or adopted, as one map — see [Conventional systems in the stack](/crosswalker/concepts/conventions/).

| Dimension | What it classifies | Crosswalker examples |
|---|---|---|
| **Artifact role** | Meaning and authority | Schema Contract; Knowledge Set; Recipe; later Execution Record and Package Manifest |
| **Representation tier** | Where knowledge is represented | Tier 0 source; Tier 1 canonical managed Markdown; Tier 2 derived SQLite projection/cache |
| **Logical layer** | System responsibility | Import, storage, projection, query, export, audit |
| **Lifecycle capability** | Recurring outcome | Acquire, Shape, Connect, Understand, Share, Maintain |

No generalized `KnowledgeSet` schema is claimed in v0.1. Tier 1 is the canonical representation/authority tier in which concrete Knowledge Sets are materialized; it is not itself a root artifact class.

**Three representation tiers, simply:**

- **Tier 0** = upstream source data in whatever representation it arrives
- **Tier 1** = Crosswalker's canonical managed Markdown representation and local authority tier for Knowledge Sets
- **Tier 2** = a deletable SQLite projection/cache derived from Tier 1 for fast queries

**Six logical layers, simply:**

| # | Layer | What it does | Where it operates |
|---|---|---|---|
| 1 | **Import** | Read source → write canonical Markdown | T0 → T1 |
| 2 | **Storage** | Hold canonical state on disk | T1 (also T2 once projected) |
| 3 | **Projection** | Read T1 → write T2 (the projector) | T1 → T2 |
| 4 | **Query** | Answer user questions over T1 + T2 | T1, T2 → user |
| 5 | **Export** | Read T1 (or T2) → write external formats | T1, T2 → external |
| 6 | **Audit** | Track who-changed-what + integrity | git, signed manifests |

The rest of this page expands each layer with diagrams, components, and code references.

## The simplified picture

Three rules that make the whole architecture tractable:

1. **Tier 1 is canonical local managed authority.** Tier 0 is upstream; Tier 2, views, snapshots, and exports are derived. No authoritative Crosswalker-managed knowledge lives only in Tier 2.
2. **Tier 2 is deletable.** If `.crosswalker.sqlite` is missing, corrupted, or stale, the projector rebuilds it from T1 on next vault load. This is what makes Tier 2 risk-free to bundle ([Ch 24 §2](/crosswalker/agent-context/zz-log/2026-05-04-tier-2-substrate-synthesis/)).
3. **Schema Contracts govern producer boundaries.** The **Tier 1 Schema Contract** makes conforming Tier 1 emitters first-class; the separate **Recipe Schema Contract** governs ImportRecipe specifications. The engine is replaceable ([schema-as-primitive commitment](/crosswalker/concepts/etl-and-import/#the-reframe--schema-is-the-primitive-etl-is-convenience)).

These rules preserve two independent authorities: extensional Knowledge Sets represented canonically in Tier 1, and intensional Recipes represented canonically under the Recipe Schema. Neither should be reconstructed from a smaller implementation view model.

## The three representation/storage tiers

| Tier | What it is | Lifetime | Authority | Governing contract |
|---|---|---|---|---|
| **Tier 0** | Upstream source data in whatever shape it ships (CSV, JSON, JSONL, XLSX, OSCAL, etc.) | Whenever the user or publisher has it | Upstream authority may exist, but Tier 0 is not Crosswalker's managed authority | n/a (source-specific contracts may apply) |
| **Tier 1** | Canonical Crosswalker-managed Markdown representation of concepts and assertions | Permanent (git-tracked) | **Authoritative local managed knowledge** | Tier 1 Schema Contract in [`spec/tier1.schema.json`](https://github.com/cybersader/crosswalker/blob/main/spec/tier1.schema.json) |
| **Tier 2** | `.crosswalker.sqlite` sidecar — a qualified Tier 1 → Tier 2 SQL projection | Recreatable on demand | Derived; never independently authoritative | [v0.1 schema spec §7](/crosswalker/agent-context/v0-1-schema-spec/#7-tier-2-sidecar-sql-schema-sqlite-wasm-projection) |

**What "canonical" means**: every field in Tier 2 has to be derivable from Tier 1 frontmatter. Every queryable Tier 1 frontmatter field has to be a flat scalar or wikilink (no nested objects, no inline expressions) so it's [Bases-queryable](/crosswalker/concepts/metadata-ecosystem/) directly without going through T2.

**What's NOT a tier**:
- `ParsedData`, `ConceptIdentity`, and `Address` are implementation/runtime values, not tiers or domain artifacts (see [ETL concept "What ParsedData is"](/crosswalker/concepts/etl-and-import/#what-parseddata-is-and-isnt)).
- [ImportRecipe](/crosswalker/concepts/terminology/#import-recipe) is an intensional Recipe artifact adjacent to generation, governed by `spec/recipe.schema.json`; it is not inside Tier 1 and is not ontology content.
- A [MappingSet](/crosswalker/concepts/terminology/#mapping-set) is a Knowledge Set subtype; each MappingAssertion may be represented by a Tier 1 member record, but the tier is not the set.
- The closure cache is not a separate tier; it is a materialized cache inside Tier 2.
- Live Bases views and materialized snapshots are derivative renditions, not new tiers.

### Two-mode architecture

The import layer supports **two architectural modes** ([decided 2026-05-05](/crosswalker/agent-context/zz-log/2026-05-05-two-mode-architecture/)):

- **Mode 1 — bundled projector**: external producer (or wizard) hands the bundled engine structured rows + recipe → engine emits Tier 1
- **Mode 2 — direct emission**: external producer (AI agent, MCP server, marketplace bundle) writes Tier 1 Markdown directly, bypassing the bundled engine

Both are first-class. ChunkyCSV / JSONaut / dbt are natural Mode 1 feeders. AI agents are natural Mode 2 emitters. See [ETL concept "two-mode architecture"](/crosswalker/concepts/etl-and-import/#the-two-mode-architecture--bundled-projector-or-direct-emission) for the full picture.

### Properties of Tier 1 storage

- **Representation, not root artifact**: Tier 1 files materialize member records from one or more Knowledge Sets under a canonical local managed authority tier
- **File-based**: every concept, evidence link, and crosswalk assertion is represented by its own `.md` file
- **YAML frontmatter is the data**: per Ch 22 §1.3, frontmatter is flat-scalar / wikilink only, not nested objects
- **git-tracked**: every change is a commit ([v0.1.8 audit trail](/crosswalker/reference/roadmap/milestones/v0-1-8-audit-trail/))
- **Obsidian-native**: files appear in the file explorer, search, graph view, Bases queries, etc., natively
- **Survives plugin uninstall**: even with no plugins enabled, the vault is still readable Markdown
- **Three Tier 1 member-record shapes** discriminated by `kind` — concept / junction-note / crosswalk-edge ([Tier 1 Schema Contract](/crosswalker/agent-context/v0-1-schema-spec/)). They express different assertion shapes; v0.1 does not claim a generalized KnowledgeSet aggregate schema.

### Why files instead of a database

See [`concepts/file-based-graph-database`](/crosswalker/concepts/file-based-graph-database/) for the full philosophical case. Short version: files are diffable, mergeable, exportable, archivable, attestable, and survive every tool/plugin in the stack getting replaced.

### Recovery property (load-bearing)

If `.crosswalker.sqlite` is missing, corrupted, or stale, the projector reprojects from canonical Tier 1 on next vault load. **This is what makes Tier 2 risk-free to bundle.** Per [Ch 24 §2](/crosswalker/agent-context/zz-log/2026-05-04-tier-2-substrate-synthesis/) — the modularity rule that lets us swap substrates (libSQL/Limbo/server) without data migration.

### Substrate

`@sqlite.org/sqlite-wasm` (canonical, foundation-governed). `sqlite-vec` deferred — see the [WASM-A path notes in v0.1.5](/crosswalker/reference/roadmap/milestones/v0-1-5-tier-2-sidecar/#path-history--wasm-b-attempted-reverted-to-wasm-a-2026-05-05--2026-05-06) and the calendar-anchored 2026-11-06 revisit checkpoint in [Ch 24 §5 Q4](/crosswalker/agent-context/zz-log/2026-05-04-tier-2-substrate-synthesis/#5-migration-triggers--when-to-revisit).

## Layer 4 — Query (T1 + T2 → user)

**One-liner**: let users ask questions over their vault — Bases provides live views over T1; SQL handles joined or transitive reads over the derived T2 projection; materialized snapshots persist selected point-in-time results separately.

```
                        QUERY LAYER

   User question                  Routing decision
   ─────────────                  ────────────────
   "Show me all NIST          ─►  Bases over Tier 1 frontmatter
    AC-family controls"           (file.hasTag('framework/nist/ac'))

   "What evidence covers      ─►  Bases over Tier 1 frontmatter
    AC-2?"                        (junction-note where subject == AC-2)

   "Which CSF                 ─►  Bases (simple case) OR SQL (cross-
    subcategories map to          ontology join)
    NIST AC-family?"

   "Show all controls         ─►  SQL recursive CTE over mappings
    NIST CSF Identify             table (Tier 2; closure_cache
    maps to via any chain         materialized on first call)
    of crosswalks"

   "Coverage matrix:          ─►  SQL join over concepts ×
    every control × every         mappings × junction_notes
    framework that maps           (Tier 2)
    to it × evidence count"
```

### Components in this layer

| Component | Code | What it does |
|---|---|---|
| **Bases (upstream Obsidian)** | n/a (built-in to Obsidian) | Flat YAML-frontmatter queries directly over Tier 1 — no plugin needed |
| **SQL query helpers** | `src/tier2/queries.ts` (v0.1.5 Phase 3) | Typed `getControlsByOntology`, `findCoverageGaps`, `crosswalkBetween`, `closureFromConcept` |
| **Bases query templates emitted in concept-note bodies** | Body-template rendering in `src/render/body.ts` + `src/render/template.ts` (v0.1.6); no separate templates directory | Recipe-author authors a body template; engine emits a working Bases query in each concept note |

### When to use which

| Question shape | Tier | Why |
|---|---|---|
| Flat key/value over a single note kind | **Tier 1 via Bases** | Native; no plugin; survives Tier 2 corruption |
| Tag-prefix or single-frontmatter-field filter | **Tier 1 via Bases** | Same |
| Multi-ontology joins | **Tier 2 via SQL** | Bases doesn't do joins; SQL does |
| Transitive closure (chain of crosswalks) | **Tier 2 via SQL recursive CTE** | Depth-covered cache partitions safely reuse equal or shallower queries; deeper queries extend coverage |
| Coverage matrix (controls × evidence × frameworks) | **Tier 2 via SQL** | Multi-table join; awkward in Bases |
| Vector / semantic similarity | **Tier 2 via sqlite-vec** | Deferred to a future milestone (see Ch 24 §5 Q4) |

The choice is the recipe author's (or query author's). Tier 1 is the default for simple queries because it survives Tier 2 corruption. Tier 2 is for when SQL's expressivity is needed.

A **live view** evaluates current data when opened or refreshed; Bases views belong here. A **materialized snapshot** persists query results at a point in time and can become stale. Snapshots are useful derivative evidence and publishing fallbacks, but they do not become canonical Knowledge Sets merely because they are stored in the vault.

### Three-layer query engine architecture

The query layer separates concerns across three orthogonal layers (settled 2026-05-08; see [synthesis log](/crosswalker/agent-context/zz-log/2026-05-07-bases-query-layer-architecture-synthesis/)):

| Layer | Vocabulary | Concept page |
|---|---|---|
| **A — Query primitives** | filter / traverse / bind / project / aggregate / anti-join / set-op / diff | [query-primitives](/crosswalker/concepts/query-primitives/) |
| **B — View shapes** | table / list / pivot / graph / hierarchy / timeline | [view-shapes](/crosswalker/concepts/view-shapes/) |
| **C — Recipes / reports** | "Coverage Matrix", "Crosswalk Density", "Ontology Overlap", etc. | recipe registry |

### Query verbs × mechanisms

The canonical Layer A vocabulary is the 8 query verbs — `filter`, `traverse`, `bind`, `project`, `aggregate`, `anti-join`, `set-op`, `diff` (locked by Ch 29, 2026-05-09; `closure` folded into `traverse(depth=*)`, `pivot` demoted to a Layer B view shape).

Each verb executes on one of four mechanisms: Bases-native, Tier 2 SQL helpers, codeblock processor (v0.1.7), or materialized snapshot (v0.1.8).

[**query-primitives**](/crosswalker/concepts/query-primitives/) holds the single verb-to-mechanism table; it is not duplicated here.

Crosswalker recipes (Layer C) name a primitive composition + a view shape. The engine picks the right mechanism for each primitive based on what's expressible at that layer. v0.1.6 ships the `crosswalkerPivot` custom Bases view (`registerBasesView`) for the pivot shape; v0.1.7 ships the `crosswalker-query` codeblock processor; v0.1.8 ships materialized snapshot output.

[v0.1.6](/crosswalker/reference/roadmap/milestones/v0-1-6-bases-query-layer/) (Bases templates + `crosswalkerPivot` custom view + recipe loader); [v0.1.7](/crosswalker/reference/roadmap/milestones/v0-1-7-exporters/) (codeblock processor); [v0.1.8](/crosswalker/reference/roadmap/milestones/v0-1-8-audit-trail/) (materialized snapshot output).

### Round-trip determinism

The export layer commits to **byte-identical round-trip**: import a STRM TSV → export the resulting Tier 1 vault → STRM TSV bytes match. This is enforced by tests in v0.1.7. Importing your own export and re-exporting must be a fixed point.

## Layer 6 — Audit (cross-cutting)

**One-liner**: track who-changed-what, when, with what integrity guarantees.

Audit implementation objects are not automatically the later administrative artifact contracts. A future **Execution Record** will separately report one bound Recipe run; a future **Package Manifest** will separately resolve a distributed release. Per-note `_crosswalker` provenance, git commits, and the planned v0.1 audit manifest are narrower records, not those complete envelopes.

```
                         AUDIT LAYER

   Tier 1 = git commits (T1 audit floor)
            ─────────────────────────
            Every generation pass produces one commit
            Commit message includes recipe id + recipe hash +
            concept count + summary diff
            git log + git blame are the audit trail

                   +
            ────────────────────────────────────────────
            Optional Ed25519-signed audit manifests
            for shared mapping bundles
            (not yet a Package Manifest contract)

                   +
            ────────────────────────────────────────────

   Tier 2/Tier 3 audit profiles (deferred to v1.0+):

            All opt-in compliance-export mode (per Ch 13/15)
```

## Read/write data flow

Which components read/write which storage tier:

| Tier | Written by | Read by |
|---|---|---|
| **T0** (source) | the user (or external producer) | Source parser |
| **T1** (canonical Markdown) | Generation engine; external Mode 2 producers | Bases queries; projector; exporters; git audit |
| **T2** (SQLite sidecar) | Sidecar lifecycle (open + migrations); projector; closure cache populator | SQL query helpers; exporters (when joining over T2 tables) |
| **External** (TSV / JSON / PDF) | Exporters; FRE 902(13) PDF generator | (downstream tools — Excel, OSCAL validators, courts) |

Notice that **every derived knowledge rendition ultimately traces back to Tier 1**: T0 plus an ImportRecipe produces T1, T2 derives from T1, exports come from T1 (or T2 which derives from T1), and audit hashes T1. No authoritative managed knowledge lives only in T2.

The ImportRecipe is intentionally absent from the tier table: it is an adjacent intensional artifact governed by the Recipe Schema Contract. A MappingSet or ontology is extensional knowledge represented through Tier 1 member records. A future Execution Record and Package Manifest will be separate administrative envelopes rather than new tiers.
